# サウンドチェック / Sound Check

音を測るブラウザSPA。会議の録音環境から会場のPAまで。
トップページで道具を選び、それぞれのURLで動く。

| 機能 | URL | 状態 | 何を測るか |
|---|---|---|---|
| 音質チェック | `/quality` | 動く | 録音した音声が会議に使えるかを5軸で採点する |
| ボリュームチェック | `/volume` | 動く | 会場の音量を測り、ミキサーで動かした量を数値で見る |
| ハウリングチェック | `/howling` | 動く | 鳴っているハウリングの周波数を特定する |

共通層は使う人が現れてから切り出す方針なので、
[受動リアルタイムモニターの骨格](docs/design/realtime-monitor.md)のうち
`lib/` に出してあるのはマイクの取り込みと状態機械の2つだけである。
フレーム化と移動窓は共通化していない——予告していたが、2つ書いてみたら形が違った。

- [シェルとトップページの設計](docs/design/shell.md)
- [ボリュームチェックの設計](docs/design/volume.md)
- [ハウリングチェックの設計](docs/design/howling.md)

## ハウリングチェック

鳴っていることは部屋の全員が耳で分かります。分からないのは
**3.2kHz なのか 4.5kHz なのか**だけで、この道具はそこだけを数値にします。

```
   発振中
   4k帯 ／ 3.20 kHz
```

固定バンドのグライコしか無い現場では「4k帯」がそのまま操作になり、
パラメトリックEQがあるなら数値が効きます。**利用者はEQを触れる人に限定**しています。

想定している使い方は「**ハウった後に開いて、次に鳴くのを捕まえる**」です。
イベント中ずっと動かし続ける前提は取っていません。

- **鳴き終わった周波数は次の発振まで残す** — オペレーターが画面を見るのは鳴き止んだ後。
  ケーブルを挿し直したり人と話したりで平気で30秒経つので、時間で消すと画面を開いた
  理由そのものが消える。誤読は経過秒（「3分20秒前」）の併記で防ぐ
- **直近3件まで、同じ周波数は回数でまとめる** — `3.2kHz → 3.2kHz → 5kHz` という
  並びそのものが診断になる（3.2kHzを切ったせいで次のピークが出た、と読める）
- **状態は2つだけ（聞いています／発振中）** — 「注意」は作らなかった。咳や拍手で光り、
  周波数も出ないので行動に変換できない。何度も光れば画面を見るのをやめる
- **バーはレベル(RTA)ではなく突出度** — 素直なレベルだと最も高いバーは常に人の声の
  帯域になり、検出しているものがバーに現れない。突出度なら表示と判定が同じ量になる
- **持続の要求は 250ms** — 腕のいいオペレーターはハウリングを 0.2〜0.5秒で殺す。
  設計時の 500ms では「下手な現場でだけ動く道具」になる
- **倍音列は発振と呼ばない** — 伸ばした歌声・シンセのパッド・電源ハムは、細いピークとして
  数秒持続するので「突出＋持続」だけでは区別がつかない
- **入力が割れたら申告する** — 大きく鳴るほど端末のマイクが飽和し、歪みが周辺の中央値を
  持ち上げて検出しにくくなる。**鳴きが大きいほど黙る**のがこの道具の唯一の
  「静かに間違える」経路なので、黙る代わりに言う
- **計測が止まったら止まったと言い、再開できる** — 「何も鳴っていない」と
  「何も測っていない」が同じ見た目になるのを防ぐ。止まる直前に捕まえた周波数は
  残す（勝手に止まったときまで消すと、この道具を開いた理由が消える）が、
  経過秒は捨てる——何分経ったか分からないのに「12秒前」と出すのが最悪の誤読なので

**予兆（なきかけ）は判定しません。** 空調・ファン・持続音と区別がつかず、空調を指して
「危険」と言い出したツールは二度と信用されないからです。突出度そのものはバーで
見せますが、断定はしません。**音も出しません**（AECを切ったまま自分で音を出すと、
ツール自体がハウリングを起こしうるため）。

表示バンドは **250 / 500 / 1k / 2k / 4k / 8k**（Hz）。63Hz帯と125Hz帯は載せていません
——48kHz・FFT4096 ではビンが低すぎて、突出度を測るための下側の近傍が取れないためです。
**測れないものの箱だけを並べない**という方針で、実際に125Hz帯を載せていたときは
基音110Hzの歌声を誤検出しました。

検証は合成信号で行い、**適合率 1.0 / 再現率 1.0**（陽性7件・陰性12件）です。
陰性には電源ハム・拍手・伸ばした歌声・BGMのパッド・プロジェクタのファンを含みます。
詳細は[ハウリングチェックの設計](docs/design/howling.md)を参照してください。

## ボリュームチェック

会場でPAから流れている音をマイクで拾い続け、「基準を計測する」を押した時点からの
変化量を dB で表示します。フェーダーをどれだけ動かしたかが数値で見えます。

- **開いた時点で測り始める** — 開始ボタンだけの画面は挟まない。マイクを開かないと
  何も表示できない機能なので、その画面には読んで決めることが無い（起動に失敗したときと、
  自分で停止したあとだけ、説明と開始ボタンの画面に戻る）
- **A特性で重み付け** — フラットなRMSでは低域が数字を支配するが、低域は定在波で
  場所ごとに10dB以上変わり、スマホの内蔵マイクはそもそも100Hz以下を拾えない
- **平均するのは声だけ。窓は「実時間の10秒」ではなく「声の10秒」** — 会場で鳴って
  いるのはマイクを通した人の声で、間が空く。全フレームを平均すると数値が喋りの密度で
  動き、フェーダーに触れていないのに差が出る（実測: 間0.3秒の区間で基準を取り
  間2.0秒の区間と比べると最大 1.70dB。声だけで平均すれば 0.16dB）
- **残り秒数はすべて「声の秒数」だと画面に書く** — 誰も喋っていない間は減らない。
  とくに収束の残り秒数は「次に操作していいのはいつか」を決めるために読まれるので、
  壁時計と取り違えられるといちばん重い。壁時計への換算は未来の喋りの密度の予測になり、
  外れれば残り秒数が増える（＝巻き戻る）
- **声が足りないときは、最後に十分な声で測れた値を経過秒つきで残す** — 消す設計だと
  話者交代のたびに主役の数字が消える。凍らせるのは「声が消えた瞬間の値」ではなく
  「窓に十分な声があった最後の値」——前者はその回でいちばん当てにならない平均になる。
  保持中にレベルが動いたら捨てる（古いことは経過秒で伝わるが、「あなたがさっき
  動かした分は入っていない」ことは伝わらないため）
- **拍手・映像・BGM だけの区間は数値を出さない** — 有音の判定は「声の検出」ではなく
  「大きい側の検出」なので、拍手は素通りする。そのままだと**ゲートを入れる前より
  はっきり間違った数値**が出る。基準を取ったときのスペクトルの形を憶えておき、
  離れたら黙る（話者交代では黙らない。実測で話者交代は 1.6〜2.9dB、拍手は 10.1dB）
- **比較は直近の声10秒ぶんの等価レベル(Leq)** — PAの音は瞬間ごとに10dB以上揺れるので、
  瞬時値どうしを引き算しても操作量が決まらない。バーだけ瞬時値で動かす
- **音割れは直近10秒のうち割れていた時間で出す** — 原因を取り除けば自動で消える。
  「回数」では数えられない（クリップした波形は半周期ごとに閾値を下回るので桁が壊れる）
- **基準は押した時点から先の声10秒ぶんで測る** — 遡ると、押す前のレベル変化（客席へ歩く、
  演目が変わる）が基準に焼き付き、フェーダーに触れていないのに差が出続ける
  （実測: 押す5秒前に +6dB あると遡る窓は 2.0〜4.7dB ずれる）。遡らないので
  窓が埋まるのを待たずに押せる
- **基準はリロードをまたいで残す** — マイク名が一致し10分以内のときだけ復元し、
  復元したことを画面に出す。黙って使い始めると `+0.0 dB` から動くので、
  取られたことに気づけない。`停止` と `基準を消す` は保存したぶんも消す
  （生き残ってよいのは**利用者が終わりを宣言していない**消え方だけ）。
  **同じ席でリロードしたのか、歩いて席を移ってから開き直したのかは区別できない**
  ——時刻とマイク名では防げないので、復元したことを画面に出して釣り合わせている
- **フェーダーを動かした直後は「声があと N 秒ぶんで確定します」と出す** — 移動窓は操作の
  直後だと操作前と操作後の混合になる。+6dB 動かした5秒後の表示は +4.0dB で、これは
  移動窓の必然だが、**収束済みの +4.0dB と見分けがつかない**と足りないと読まれて
  もう一段動かされる
- **帯域ごとに変化量が違うときは重み付け無しの差も並べる** — 「差は正しい」が
  成り立つのは全帯域が一律に動いたときだけ。低域だけを上げると A特性の主役は
  ほとんど動かない（実測: 120Hz以下 +6dB で A +1.0dB / Z +2.5dB）
- **割れる手前で差が縮み始めたら断る** — 端末のマイクが飽和すると、まだ音割れには
  ならないのに変化量だけが小さくなる（実測: 真の +6.02dB が +5.57dB）
- **端末のAGCを切れたか確かめる** — 制約を出しただけでは通らない機種がある。
  切れていなければ、どの数字より先に「変化量は信用できません」と出す
- **使用中のマイク名を表示** — 測定対象を取り違えたまま自信のある数字を出さないため
- **計測が止まったら止まったと言う** — 端末の画面が消えるとブラウザが取り込みを止める。
  固まった「+3.5dB」は正しい測定値と見分けがつかず、そのままフェーダーを動かされる。
  1.5秒途切れたらマイクを閉じて再開ボタンを出す（**基準は持ち越す**。ただし再開時に
  別のマイクが開いていたら、感度が違うので基準を破棄して理由を出す。マイク名が
  取れず**同じ機材か確かめられないときも破棄する** — 取り直しは声10秒ぶんで済むが、
  別の機材との差は取り返せない）

**絶対音圧(dBA)は出しません。** ブラウザはマイクの感度を知らないため原理的に不可能です。
言えるのは差だけなので、適正・不適正の判定も出しません。

**まだ捕まえられないものが2つあります。** ①声の下に敷かれた BGM——音源が入れ替わる
わけではないので形が変わらず、それでいてレベルは上がる（実測で、声より 6dB 下の BGM で
0.8dB の誤差。3dB 下まで来ると形の照合に引っかかって黙る）。②基準から 12dB を超えて
下げた操作——「フェーダーを大きく下げた」と「番組が止まって暗騒音だけになった」は
マイクから見て同じなので、確信を持った数字を出すより古い値だと言うほうを採っています。

検証は `node validation/volume-gate.ts` で、声は実音声（CMU Arctic）、**拍手と BGM は
合成の代用**です。結果は[実測表](validation/volume-gate.md)にあります。

## 音質チェック

WAV・MP3ファイルやマイク録音から、**会議の録音環境としてどのレベルか**を
5軸で客観的に判定する。

判定の閾値は既存規格に置いている（ITU-T P.56 の有効音声レベル、
ISO 3382 の残響時間、ITU-T の広帯域音声帯域）。絶対音圧(dBA)は扱わない——
ブラウザはマイク感度を知らないため dBFS からの換算は原理的に不可能で、
ノイズは相対値(SNR)でしか語れないからである。

### 音質チェックの中身

- **ファイル解析** — WAV / MP3 をドロップまたはクリックして選択
- **マイク録音** — 10秒間録音してその場で解析
- **5軸スコアリング**（各軸の満点を合算して100点）
  | 軸 | 配点 | 測っているもの | 分類 |
  |---|---|---|---|
  | ノイズ (Noise) | 25点 | 声に対する背景雑音の比 (SNR) | 環境 |
  | 周波数バランス (Frequency) | 25点 | 有効帯域(15) / 1kHz以上の傾斜(10) | コーデック・マイク特性/距離 |
  | 残響 (Reverberation) | 20点 | 部屋の残響時間 (RT60) | 環境 |
  | 音量 (Volume) | 15点 | 発話区間の音量レベル | 機材設定 |
  | 音割れ (Clipping) | 15点 | クリッピングのなさ | 機材設定 |
- **判定** — 「このまま会議していいのか」を結論として提示。
  総合点の平均ではなく**最も低い軸**で決める（録音環境は最も弱い要因で使えなくなる）
- **実測値の表示** — 点数ではなく物理量を先に見せる
  （SNR / 残響時間 / 帯域上限 / 発話レベル / クリップ率）
- **加工済み音声の警告** — Zoom/Teams録音のようにノイズ抑制や帯域制限が
  かかった音声を検出し、影響を受ける軸に「参考値」バッジを付ける
- **読み上げ文の案内** — 発話区間と無音区間の両方が無いとSNRも残響も測れないため、
  録音前に例文と緩い指示を提示する
- **VUメーター** — 総合スコアをアナログ風に表示
- **レーダーチャート** — 5軸を一覧で可視化。幅があるときは
  「総合点／判定」「レーダー／内訳」が対になって2列に並ぶ（2列に割る判断は
  ビューポートではなく結果領域の幅で行う）
- **音声再生** — 解析後にアップロード/録音した音声を再生
- **JA/EN 切替** — ブラウザ言語を初期値とし、`localStorage` に保持

## ディレクトリ構成

```
src/
  App.svelte              シェル。ルーティングとヘッダーだけを持つ
  shell/                  機能に依らない層（ルーター・言語・共通CSS）
  pages/                  メニュー
  features/
    registry.ts           機能の一覧。ここに1行足すとメニューとURLが増える
    quality/              音質チェック（解析・採点・画面・アイコン・文言・テスト）
    volume/               ボリュームチェック（測定・画面・アイコン・文言・テスト）
    howling/              ハウリングチェック（検出・画面・アイコン・文言・テスト）
  lib/
    audio/                音の出入り（マイク取り込み・監視の状態機械・WAV）
    dsp/                  信号処理（統計・FFT・スペクトル・ピーク・biquad・
                          聴感補正・オクターブバンド）
    stream/               終わりの無い流れの骨組み（フレーム化・移動窓・環状バッファ）
    format.ts             画面に出す数値の整形
  test-support/           テスト専用の合成信号。製品には載らない
```

機能を1つ足すときに触るのは `features/<名前>/` と `features/registry.ts` だけになる。
registry の1行が持つのは URL・文言・コンポーネント・**アイコン・色**で、
メニューのタイルはそこから導出される。

`lib/` と `features/` の線引きは**「測り方」か「何と呼ぶか」か**である。
FFT・突出度・オクターブバンドの定義・フレーム化は `lib/`。閾値と、何を発振や
音割れと呼ぶかは各機能が絶対値で持つ——尺度が違うものを共有すると、片方を
動かしたときにもう片方が黙って壊れる。
**解析パイプラインと状態機械は機能ごとに独立させる。** 音質チェックはバッチ
（録って解析して採点）、ハウリングとボリュームは受動リアルタイム（終わりが無く点数も無い）で、
共通の状態機械に乗せると両方が歪むため。

## 判定精度の検証

推定器が既知の物理量を復元できるかを実測します。人間によるラベル付けは不要です。

```bash
npm run generate     # 既知のSNR/RT60/カットオフ/クリップ率を注入した検証セットを生成
npm run validate     # 推定誤差とスコアの単調性を実測してレポートを出力
```

素材は3通り選べます。既定の取得元は WAV 配布なので **ffmpeg は不要**です。

```bash
npm run fetch-corpus -- --list   # 取得元の一覧
npm run fetch-corpus             # 既定 (CMU ARCTIC, 約115MB) を取得
```

コーパスを置かない場合は合成音声風信号で自動的に代替されます。
取得した音声は `fixtures/`（git管理外）に置かれます。

直近の実測値（**実音声** CMU ARCTIC 4話者 × 16kHz/48kHz・240条件）:

| 推定対象 | バイアス | MAE | 最大誤差 |
|---|---:|---:|---:|
| 帯域上限 | -6.1 Hz | 6.1 Hz | 100 Hz |
| 1kHz以上の傾斜 | -0.26 dB/oct | 0.75 dB/oct | 2.99 dB/oct |
| 有効音声レベル | 0 dB | 0 dB | 0 dB |
| クリップ率 | 0 | 0 | 0 |
| SNR | +0.30 dB | 1.60 dB | 5.38 dB |
| 残響時間 (RT60) | -0.110 秒 | 0.173 秒 | 0.891 秒 |

話者は米女性・米男性・インド英語男性・スコットランド英語男性の4名。

**この表の読み方に2つ断りがあります。**

- **有効音声レベルとクリップ率の「0」は恒等式です。** 真値の計算が推定器と同じ式
  （レベルは p95−25dB の有音判定、クリップは同じ 0.98 / 0.01 の閾値）なので、
  一致するのは構成上あたりまえです。この2行が確認しているのは
  「計数のループが壊れていないこと」だけで、推定の正しさではありません。
- **これらは in-sample の数値です。** ノイズフロアのパーセンタイル、減衰の起点、
  カットオフ点といった定数は、同じ素材の上で掃引して選んでいます。
  ホールドアウトは取っていないので、未知の素材ではこれより悪くなります。

スコアの向きの検証（Spearman順位相関）は1件を除いて想定どおりです。
**残っている1件は打鍵音のような衝撃性ノイズで、ノイズ軸が反応しません**
（`blind`。真SNR 15dB を 30dB 前後と読み、バイアス +9.4dB）。
継続時間が短いので無音区間の選定をほとんど汚さず、ノイズフロアの推定が
静かなまま残るためです。この録音では「この録音について」に申告を出します。

検証条件のうち、次の4つは劣化の作り方が現実の1次元に寄っていたのを広げたものです。
詳細は [validation/README.md](validation/README.md) を参照してください。

| 条件 | 分かったこと |
|---|---|
| 帯域ごとにRT60が違う応答 | 推定器は最も遅く減衰する帯域に引っ張られる。低域だけ長い部屋で真値 0.4秒を 0.8秒と読む（平坦な応答では -0.05秒しかずれない） |
| 多人数の話し声 | 定常ノイズと同程度に測れている（MAE 1.4dB） |
| 打鍵音 | 上記のとおり測れていない |
| 間（無音区間）を間引いた発話 | SNRを 4.1dB 悲観的に読む（MAE 4.7dB）。**ノイズ軸は間の取り方に依存しています** |

製品のマイク録音は48kHzなので、`--rates=16000,48000` で同じ内容を両方の
レートで測っています。素材ごとの誤差の差は SNR で0.2dB以内、RT60で0.04秒以内
でした（推定器の定数は秒/Hzで書いてありますが、FFT長だけは2048固定なので
48kHzでは周波数分解能が3倍粗くなります。そこが効いていないことの確認）。

残響時間は減衰イベントが4件未満だと誤差が大きくなるため、そこは「参考値」として
開示します。確定値として出す行だけを見ると MAE 0.052秒 / 最大 0.133秒で、
最大誤差 0.486秒の行はすべて参考値として開示されています。

RT60の最大誤差は生成の乱数系列に敏感です（3回の生成で 0.37 / 0.845 / 0.486 秒）。
MAEは 0.072〜0.105 秒で安定するので、最大誤差の値を単独で読まないでください。

`fixtures/real/` に実録音を置くと、製品と同じ復号経路で解析した結果を出力します
（`npx vitest run src/features/quality/real-material.test.ts --reporter=verbose`）。
m4a のような非可逆形式もブラウザのコーデックで読めます。素材が無ければ黙って通るので、
素材を git に入れる必要はありません。実録音の真値は誰も知らないので、ここで確かめるのは
値の正しさではなく「壊れず、範囲内の値を返し、測れていないものを黙って部分点にしない」ことです。
アドバイス（助言）も注入した物理量から真値を作って検証しています。「帯域上限が7kHz未満
なら帯域不足の助言が出るべき」のように条件ごとに出るべき/出るべきでないが決まるので、
適合率と再現率が測れます。**空振りは見落としより重い**という前提で閾値を選んでいます
（直さなくてよいものを直せと言うほうが道具への信頼を損なうため）。

助言の閾値は採点の境界とは別に、すべて絶対値で持っています。採点は品質の尺度
（満点＝スタジオ品質）、助言は明瞭度の基準です。混ぜると採点の満点を動かしたときに
助言が黙って壊れます（実際に一度壊しました）。

軸の配点（ノイズ25 / 周波数25 / 残響20 / 音量15 / 音割れ15）は、複合条件を使って
DNSMOSとの順位相関で検証しています。モデルが判断できる要因（ノイズ・残響）だけに
絞ると ρ=0.800 で、試した配点候補すべてが 0.775〜0.800 に並びました——検出できる
誤りは無く、同時にこの方法でこれ以上絞り込むこともできません。**周波数軸と音割れ軸の
配点は原理的に検証できません**（モデルは8kHz超の帯域差を見られず、クリップ率を100倍
にしてもMOSは0.155しか動きません）。

任意で、人間の主観評価で学習された無参照品質推定モデル（DNSMOS）との
順位相関も測れます。**モデルは製品には載せません**——開発時に係数を調整する
方向を得るためだけに使います。

```bash
npm run fetch-mos-model      # モデルを取得（約1.1MB, git管理外）
npm run validate -- --mos
```

詳細は [validation/README.md](validation/README.md)、最新の結果は
[validation/report.md](validation/report.md) を参照してください。

## スコアの判定基準

| スコア | グレード |
|---|---|
| 70〜100 | 優秀 (Excellent) |
| 50〜69 | 良好 (Good) |
| 35〜49 | 普通 (Fair) |
| 0〜34 | 要改善 (Poor) |

なお総合点は要約であり、判定そのものではありません。実際の判定は
各軸の達成率のうち**最も低いもの**で決まります（55%以上で「十分」、
35%以上で「使えるが改善の余地あり」、それ未満で「適していない」）。

**測定値が境界の誤差圏内にあるときは断定しません。** 判定は3値なので、
問うべきは「点数の誤差が何点か」ではなく「同じ部屋を測り直して同じ答えが出るか」です。
実測すると出ませんでした——真の残響時間を 0.7秒（ANSI/ASA S12.60 が教室に許す上限）に
固定して話者と部屋の実現だけを振ると、判定が「十分」「使える」「適していない」の
3つに割れました。残響軸は 0.2〜0.9秒を20点に写すので、確定値でも残る誤差 0.093秒が
達成率 0.13 に相当し、判定の境界の間隔 0.20 に対して狭くないからです。

そこで各軸に実測誤差から決めた不確かさを持たせ、**どれか1軸でも境界の誤差圏内にある
なら「十分」と断定しない**ようにしています。下側の境界では判定そのものは動かさず、
断定していないことだけを添えます（一貫した原則は「境界では良い側に振らない」）。
軸ごとの不確かさは [validation/report.md](validation/report.md) の
「判定の不確かさの定数と実測の突き合わせ」で実測と機械的に照合しています。

## 対象範囲

**会議・音声の録音環境**に絞っています。歌や楽器の録音は対象外です。
評価軸と閾値が音声用に作られているため（例: 200Hz以下が多いと減点、
500〜3kHzが支配的だと加点）、よく録れた音楽を低く評価してしまいます。
