# 検証基盤

「判定の精度が上がった」を、主観ではなく数値で言えるようにするための仕組み。

**人間によるラベル付けは行わない。** 正解は2つの外部ソースから借りる。

1. **自分で注入した既知の物理量** — 既知SNRのノイズ、既知RT60のインパルス応答、
   既知カットオフのローパス、既知のクリップ率。推定器がそれを復元できるかは
   算数の問題なので、ラベル付けが発生しない。
2. **学習済みの無参照品質推定モデル（任意）** — DNSMOS。公開コーパスの人間の
   主観評価で学習済みなので、正解はモデル側が持っている。
   **製品には載せない。** 開発時に係数を調整する方向を得るためだけに使う。

### MOSオラクルのコストと注意

推論ランタイム `onnxruntime-node` は devDependency に入れているが、**約259MB** ある。
さらに依存の `adm-zip` に high severity の勧告がある（onnxruntime-node の
インストールスクリプト経由でのみ使われ、製品バンドルには入らない）。
MOSオラクルを使わないなら外してよい:

```bash
npm uninstall onnxruntime-node
```

外しても検証の主軸（既知の物理量の復元誤差）はそのまま動く。
`mos-oracle.ts` は未導入を検出して理由を報告し、MOS相関だけをスキップする。

### オラクルが信用できないケース

レポートには自己診断を含めている。読む前に必ず確認すること。

- **劣化なし素材のMOSが3.0未満** — 素材がモデルの学習分布から外れている。
  モデルは劣化ではなく素材そのものの不自然さを評価しているので、条件ごとの
  相関の符号を根拠にスコア設計を変えてはいけない。合成音声風信号では実際に
  2.3しか出ない。実音声で測り直すこと。
- **「異なるMOS値」が1** — その劣化がモデルに見えていない。相関に意味はない。
- **帯域制限の条件** — DNSMOS の入力は16kHzモノラルなので、8kHzを超える帯域の
  違いは原理的に見えない。8kHz以上のカットオフは全て同じ値になる。

## 使い方

```bash
npm run generate     # 検証セットを生成（コーパスが無ければ合成信号で代替）
npm run validate     # 推定誤差とスコアの単調性を実測
```

実音声を素材にする場合:

```bash
npm run fetch-corpus -- --list          # 取得元の一覧
npm run fetch-corpus                    # 既定の取得元から取得
npm run generate
npm run validate
```

製品と同じ48kHzでも測る場合:

```bash
npm run generate -- --max-sources=4 --rates=16000,48000
npm run validate
```

`--rates` を渡すと、同じ素材をレートごとに複製して1つのレポートに並べる。
素材ごとの誤差が両レートで一致していれば、サンプルレート依存の実装ミスは無い。
推定器の定数はすべて秒/Hzで書いてあるが、**FFT長だけは2048固定**なので
周波数分解能はレートに反比例する（16kHz:7.8Hz/bin → 48kHz:23.4Hz/bin）。
ここが効いていないことの確認が目的。

**注意: これは「48kHzで実装が正しく動くか」の検証であって、「48kHzの実録音で
正しいか」の検証ではない。** 16kHz素材を上げ変換しても8kHz以上に中身は生まれない
ので、8/11/16kHzのカットオフ条件は依然として試せない（自動で飛ばされる）。

MOSオラクルも使う場合（任意）:

```bash
npm run fetch-mos-model      # DNSMOS のモデルを fixtures/models/ に取得（約1.1MB）
npm run validate -- --mos
```

## git に入るもの / 入らないもの

| | git |
|---|---|
| 取得スクリプト・取得元定義 (`corpus-sources.json`) | 入る |
| 劣化パラメータと真値の記録 (`manifest.json`) | 入る |
| 検証結果 (`report.md` / `report.json`) | 入る |
| コーパスの音声 (`fixtures/corpus/`) | **入らない** |
| 生成した劣化音声 (`fixtures/generated/`) | **入らない** |
| MOSモデル (`fixtures/models/`) | **入らない** |

生成は乱数シード固定なので、`manifest.json` があれば同じ検証セットを誰でも
再生成できる。コーパス素材については SHA-256 を記録しているため、素材が
入れ替わっていれば検出できる。

## 素材の3つの経路

1. **公開コーパス** — `npm run fetch-corpus`。
   既定の取得元は**必要な本数だけ個別に取得**する（`--limit=40` で約6MB）。
   アーカイブ一括の取得元も残してあるが、検証に必要なのは数十本なので通常は不要。
   既定の取得元 (CMU ARCTIC, 約115MB) は **WAV 配布なので ffmpeg 不要**。
   LibriSpeech など FLAC 配布のものを選んだ場合だけ ffmpeg が必要。
2. **手持ちのWAV** — クリーンなモノラルWAVを `fixtures/corpus/` に直接置く。
   そのまま素材として使われる。
3. **合成音声風信号** — 上記が無い場合の自動フォールバック（`lib/speechlike.ts`）。
   声帯パルス列を3つのフォルマント共振器に通したもので、発話区間と無音区間を持つ。

3は実音声の代替ではない。**MOSとの相関（知覚量）には使えない。**
ただし「既知の物理量を復元できるか」の検証は算数なので3でも成立する。

### コーパスファイルの連結

公開コーパスの1ファイルは2〜4秒の単発発話が普通で、そのままでは短すぎる。
残響の推定には発話の切れ目が複数必要なので、製品の録音長(既定10秒)に達するまで
連ねて1素材にする。ファイル間の無音は素材自身の録音余白を使う——人工的な無音を
挿入するとデジタル無音として検出されてしまう。

目標長の80%に届かない余り物は素材にしない。息継ぎの回数が足りず、
rt60 条件だけ測定不能が増えて誤差が読めなくなるため。

素材のレベルは発話区間が -17dBFS になるよう揃える（`degrade.ts` の
`normalizeSpeechLevel`）。揃えないと、すべての条件に音量という交絡が混ざる。

## 何を測っているか

### 推定誤差

注入した真値と推定値の差。バイアス（平均誤差＝系統的なズレ）と MAE を出す。
バイアスが大きい推定器は、閾値をいくら調整しても直らない。

**真値は「注入した量」ではない。** 素材自身が持つノイズフロアも分母に含める。
これを無視すると、高いSNRを狙って注入しても実際のSNRはそこで飽和するため、
推定器が正しいのに誤差があるように見える（実際に 40dB 条件で -3.8dB の
見かけの誤差が出た）。実音声コーパスでも同じ問題が起きる。

### スコアの単調性

劣化を強めたときスコアが正しい向きに動くか。Spearman の順位相関で見る。

- `ok` — 正しい方向
- `wrong-direction` — 符号が逆。その軸は壊れている
- `blind` — まったく反応していない。その要因を測っていない
- `coupled` — 反応してはいけない条件に反応している（別要因の誤計上）

単体テストは「サイン波は高得点、スクエア波は低得点」という**順序**しか見ない。
ここでは**誤差**と**反応の有無**を見る。

相関の読み方には2つの落とし穴があり、どちらも実際に踏んだので対策済み。

- **素材をまとめて1つの相関にしてはいけない。** 素材間でスコアの水準が違うだけで
  相関が下がる。実測で帯域→周波数が 1素材 0.827 → 4素材 0.535 に落ちたが、
  素材ごとに求めると 1.0（完全に単調）だった。ρ は素材ごとに求めて平均している。
- **順位相関はスケールフリーなので効果量を併記する。** 25点満点で1.2点しか動かない
  結合と12点動く結合を同じ値で報告してしまう。実際に、無視できる結合(2.25/25点)を
  直そうとしてSNR精度を9dB犠牲にする方向へ動かしかけた。
  期待符号0の行は、相関だけでなく満点の10%以上動いているかも条件にしている。

### 軸の配点の検証（複合条件）

単独条件では**配点を検証できない**。「ノイズ25点・残響20点」が妥当かは、
「ノイズが強い録音」と「残響が長い録音」のどちらを低く評価すべきかという比較でしか
問えない。単独条件はその比較を含まない。

`--mixed` を付けると複合条件を生成する。真値が物理量ごとに定義できないので推定誤差の
集計からは外れ、MOSオラクルとの順位相関による配点の検証だけに使う。

```bash
npm run generate -- --max-sources=4 --rates=16000,48000 --mixed
npm run validate -- --mos
```

**要因は完全要因配置にしてある**（SNR 3水準 × RT60 3水準 × 音割れ 2水準 ×
帯域制限 2水準 = 36通り）。最初は「ノイズ×残響」「ノイズ×音割れ」…と組を並べたが、
それでは音割れの条件に強い残響が入らず交絡して、軸ごとの相関が音量 -0.52 /
音割れ -0.64 と符号反転して出た。軸が壊れていたのではなく条件の組み方の欠陥だった。

**オラクルが何に反応するかを先に確認すること。** レポートは軸ごとの相関を出す。
反応していない軸の配点はこの方法では決められない。実測（実音声4話者・16kHz）:

| 要因 | 範囲 | MOS | 振れ幅 |
|---|---|---|---:|
| SNR | 0 → 40 dB | 1.563 → 3.317 | 1.76 |
| RT60 | 0.2 → 1.5 秒 | 2.726 → 1.126 | 1.60 |
| クリップ率 | 0.0002 → 0.02（100倍） | 3.316 → 3.161 | **0.155** |

音割れは100倍にしてもMOSがほとんど動かない（モデルはノイズ抑制の出力で学習されて
おり音割れの訓練信号を持たない）。帯域は入力16kHzなので8kHz超が見えない。
これを知らずに相関を最大化する重みを探すと、必ず「音割れと周波数の配点を下げろ」
という答えが出る。**モデルの盲点に合わせているだけで判定は良くならない。**

レポートは条件を3つの群に分ける。根拠に使えるのは「ノイズと残響だけ」の群のみ。

## ファイル構成

```
validation/
  fetch-corpus.ts       公開コーパスの取得（curl + tar + ffmpeg）
  fetch-mos-model.ts    DNSMOS のモデル取得（任意）
  generate.ts           既知の物理量を注入して検証セットを作る
  validate.ts           推定誤差と単調性を実測してレポートを出す
  mos-oracle.ts         DNSMOS（任意・製品には載せない）
  inspect.ts            1ファイルのスペクトルを覗く（デバッグ用）
  rt60-diag.ts          残響推定の減衰イベント分布を覗く（デバッグ用）
  corpus-sources.json   取得元の定義
  manifest.json         生成した検証セットの記録（自動生成・git管理下）
  report.md / .json     検証結果（自動生成・git管理下）
  lib/
    wav.ts              WAV読み書き（ffmpeg不要）
    dsp.ts              FFT畳み込み・ローパス・リサンプル
    degrade.ts          劣化の注入（SNR / RT60 / クリップ / 帯域制限）
    speechlike.ts       合成音声風信号
    rng.ts              シード固定の乱数
    paths.ts            パスと引数
```

`lib/` は `src/lib/dsp/fft.ts` の FFT を再利用する。逆に製品コード側は
`validation/` に一切依存しない。

## デバッグ

スペクトルを覗く:

```bash
node validation/inspect.ts fixtures/generated/s0-lp3400.wav 28 42 1
#                          ファイル                        開始 終了 刻み (バンド番号)
```

残響推定の減衰イベント分布を見る:

```bash
node validation/rt60-diag.ts
```
