# Grill: ハウリングチェックの実装
Date: 2026-08-26

## Intent

**PAを触る本人が、自分のスマホで「いま鳴いたのは何Hzか」を読み取るための道具。**

鳴っていることは部屋の全員が耳で分かる。分からないのは 3.2kHz なのか 4.5kHz なのか
だけであり、そこだけを数値にする。利用者はEQを触れる人に限定する。

運用は「**ハウった後に開いて、次にハウるのを捕まえる**」。イベント中ずっと動かし
続ける前提は取らない。したがってこの道具のセッションは数分で、その99%は
「待っている時間」である。**待っている画面こそがこの道具の画面**である。

当初の依頼「5秒とか10秒で刻んで結果を出し続ける」は、次の形に置き換わった:
判定と表示は100msごとに連続、**刻みは検出履歴のほうに置く**（直近3件・止めたら消える）。
10秒バッチにすると、数字が出る頃には鳴き止んでいて道具が成立しない。

## Constraints

- 取り込み時の制約は全機能共通で変更しない（`echoCancellation` /
  `noiseSuppression` / `autoGainControl` すべて false）。特にエコーキャンセラは
  検出対象そのものをブラウザが先に消す。
- 音を出さない（能動プローブをしない）。端末のスピーカーは会場のPAではないうえ、
  AECを切ったまま自分で音を出すとツール自体がハウリングを起こしうる。
- 停止したら何も残さない。履歴・サマリ・保存を作らない。
- 点数を出さない。刻々変わるものに点数は付かない。
- 利用者の端末はオペレーターの私物スマホ。長時間運用・発熱・電池の前提を置かない。

## Key decisions

- Decision: **判定・表示は100msホップの連続。バッチにしない。** Reason: 現場では
  ハウリングは1〜2秒で殺される。10秒溜めてから解析すると、数字が出る頃には
  鳴き止んでいる。Alternative considered: 5〜10秒ごとのバッチ解析（当初の依頼の形）、
  判定窓そのものを10秒にする案。

- Decision: **検出履歴を直近3件まで持つ。同じ周波数(±3%)は1行にまとめ、
  回数・合計秒・経過秒を添える。次の発振が来るまで消えない。** Reason: 当初は
  「直近1件のホールド」で合意したが、運用が「繰り返しハウる場面で開く」と確定した
  時点で前提が変わった。3.2kHz→3.2kHz→5kHz という並びそのものが診断であり、
  最後の1件だけでは読めない。同じ周波数をまとめないと、「繰り返し鳴いている」という
  利用者が来た理由そのものが、同じ行の重複で画面を埋めてしまう。
  時間で消さないのは、鳴いた後にケーブルを挿し直したり人と話したりで平気で30秒経つため
  ——画面を開いた理由そのものが消える。古い数字の誤読は経過秒の併記で防ぐ。
  Alternative considered: 1件ホールド、10秒で消える、セッション全件のリスト。

- Decision: **FFTは 4096（既存の 2048 から変更）。表示バンドは 250Hz〜8kHz の6つ。**
  Reason: 48kHz で FFT 2048 はビン幅 23.4Hz。63Hz はビン2.7本目で、周辺中央値と
  比べる突出判定に使える下側のビンが存在しない。**光らないバーを並べるのは嘘に近い。**
  4096 なら 11.7Hz / 85ms で、演台マイクの 200〜500Hz の鳴きが測れる。ホップは
  100msのままなので表示レイテンシは変わらず、増えるのは計算量だけ。
  **実装時の修正**: 下端は当初 125Hz帯とする合意だったが、実測で外した。突出度は
  ピークの**上下両側**の中央値と比べて初めて意味を持つ。48kHz・FFT4096 では 125Hz は
  ビン10.7本目で、ガード幅(±6)を引くと下側に使えるビンが1本も残らない。片側だけの
  中央値はスペクトルの傾き（低域ほど大きい）を突出度に化けさせ、実際に**基音110Hzの
  歌声を「110Hzで発振中」と誤検出した**。250Hz帯は 176.8Hz から始まるので、
  合意の眼目だった「200〜500Hzのボワッとした鳴き」は引き続き測れる（200Hz の
  検出はテストで確認済み）。Alternative considered: 2048 のまま低域2バンドを外す、
  FFT 8192 にして 125Hz帯を残す（窓が171msになり、0.3秒の鳴きを取り逃す）。

- Decision: **倍音列の判定を入れる。検出したピーク f に対し f/2, f/3 に有意なパワーが
  あれば発振と呼ばない。** Reason: 本番中（BGM・喋りが流れている最中）を対象に含めたため。
  伸ばした歌声・シンセのパッド・楽器の音は、細いピークとして数秒持続し、
  「突出＋持続」の2条件だけでは**ハウリングと区別がつかない**。
  Alternative considered: リングアウト時（プログラム音なし）だけを対象にして判定を省く。

- Decision: **状態は2つ（聞いている / 発振中）。「注意」を作らない。** Reason: 「突出は
  あるが持続していない」状態は咳・拍手・椅子の音で光り、周波数も出さないので行動に
  変換できない。待っている数分間に何度も光れば、利用者は画面を見るのをやめる。
  「注意」の唯一の実用的な役目（道具が生きていることの提示）は、100msごとに動く
  バーのほうがうまく果たす。Alternative considered: ドキュメント通りの3状態。

- Decision: **バーは各バンドの「突出度」を出す。レベル(RTA)ではない。** Reason: 素直な
  オクターブバンドのレベルだと、会議室で最も高いバーは常に250〜500Hz（人の声）になり、
  **検出しているものがバーに現れない**。突出度なら、表示と判定が同じ量になる。
  閾値18dBに対して4kHzのバーが12→15dBと伸びるのが見える。これは「危険」と断定して
  いないので、設計が禁じた予兆*判定*には当たらない——禁じるべきは断定であって
  測定値の提示ではない。Alternative considered: レベルのバー、バー無し。

- Decision: **持続の要求は 250ms（3フレーム）。500msにしない。** Reason: 腕のいい
  オペレーターはハウリングを 0.2〜0.5秒で殺す。500ms を要求すると、その人の現場では
  一つも捕まらない——「下手な現場でだけ動く道具」になる。拍手・机を叩く音は
  インパルス（10〜20ms）で桁が2つ違うので、250msでも弾ける。250ms と 500ms の差で
  新たに拾うのは口笛・楽器の短い音であり、そこは倍音列判定が落とす。
  150ms(2フレーム)を採らないのは、たった2回の観測で断定することになるため。
  Alternative considered: 500ms、150ms。
  **事実の訂正**: grilling 中に「85ms窓が100msホップで重なる」と述べたが逆である。
  48kHz では窓(85ms) < ホップ(100ms) なので窓は重ならず、**フレームとフレームの間に
  約15msの見ていない隙間ができる**。3フレームを要求する判断は変わらない（空振りを
  重く見る以上、観測回数は多いほうがよい）が、理由は「重複の割引」ではなく
  「独立な観測を3回取るため」である。飽和の検出だけは全サンプルを見ているので、
  この隙間の影響を受けない。

- Decision: **閾値は空振り（誤検出）を重く見る側に置く。見落としは許容する。**
  Reason: プロジェクト全体の原則と結論は同じだが、**理由が違う**。音質チェックでは
  「無駄な作業をさせるから」だったが、ここでは「**利用者に検算の手段が無いから**」。
  利用者は耳でハウリングを聞いているので、見落としには気づける（鳴いたのに画面が
  動かなかった、と分かる）。空振りには気づけない——鳴いていないのに出た数字を、
  さっきの鳴きの正体だと信じてしまう。**気づける失敗より、気づけない失敗が重い。**
  Alternative considered: 見落としを重く見て閾値を緩める、判定をやめて測定値だけ出す。

- Decision: **入力の飽和（クリップ）を画面に出す。** Reason: これがこの道具の唯一の
  「静かに間違える」経路だから。ハウリングが大きいほどスマホのマイクは飽和し、
  広帯域の歪みが周辺中央値を持ち上げ、**突出度の分母が上がって検出しにくくなる**。
  つまり鳴きが大きいほど黙る。利用者からは「一番はっきり鳴いたのに画面が動かなかった」
  ＝「壊れている」に見える。他の失敗（鳴っていない・測っていない）は全て画面に出す
  設計にしたので、ここだけ塞がないと残った1つの穴に信頼が全部漏れる。表示は
  「端末を音源から離す」という行動に変換できる。**クリップ閾値の定数は
  ボリュームチェックと共有しない**（既存ルール: 尺度が違うものを共有すると
  片方を動かしたときに黙って壊れる）。Alternative considered: 出さない。

- Decision: **マイクの状態機械（idle/starting/listening/error）を `lib/` に切り出し、
  ボリュームチェックも新しい実装に載せ替える。** Reason: `VolumeCheck.svelte` の
  約70行は二重起動・許可ダイアログ中の離脱・古いチャンクの混入という、
  **間違えても気づきにくい**バグへの対処が詰まっている。書き写すと写し間違いに
  気づけない。切り出したうえで片方だけ載せ替える案は最悪で、「同じものが2つ」になり
  次に直すときどちらを直したか分からなくなる（`recordMicrophone` を残した判断とは
  状況が違う。あちらはバッチとストリーミングという*別物*が並んでいるだけ）。
  Alternative considered: 切り出してボリュームは触らない、ハウリングに書き写す。

- Decision: **フレーム化と移動窓は「入れ物」だけ共通化し、「何を積むか」は共通化しない。**
  Reason: 両実装を読み比べると、区切り方（100msごとにチャンクを切る）と
  「直近N件だけ保つ」は完全に同じだが、積むものが違う——ボリュームは波形を捨てて
  二乗和だけ持てばよく、ハウリングはFFTのために波形を4096点保持する必要がある。
  そこまで一つにすると、ボリュームに要らない波形を持たせることになる。
  `lib/stream/frames.ts` に `FrameSplitter` / `RingWindow` / `SampleRing` を置き、
  積む中身は各機能に残した。**予告は半分当たった。**

- Decision: **「聞いている」間だけ best-effort で Screen Wake Lock を取る。
  取れなくても失敗にしない。** Reason: 長時間運用はしないが、数分待つつもりの計測を
  iOSの30秒オートロックが黙って殺す。Alternative considered: 入れない
  （ボリュームチェックの判断）、常時運用前提で本格的に対応する。

- Decision: **チャンクが途切れたら「計測が止まっています」を出す。** Reason:
  「何も鳴っていない」と「何も測っていない」が同じ見た目になるのを防ぐ。

## Surfaced assumptions

- 利用者はEQ（グライコまたはパラメトリック）を触れる人に限定している。触れない人
  （会場スタッフ・司会者）にとって「3.2kHz」は行動に変換できず、打てる手は
  ゲインを下げる・マイクを動かすの3つだけで周波数は関係ない。その人向けに作ると
  この道具は「対処法を教えるアプリ」になり、**測定である必要が無くなる**。
- ある1つのフェーダー位置で発振するのは、ループゲインが最初に1を超えた1周波数だけ。
  複数が同時に鳴くのは稀で、「切ったら次が鳴く」は人がEQを触った**後**に起きる。
- スマホのハードウェアリミッタは `autoGainControl: false` では切れない。
- 利用者は耳でハウリングを聞いているので、この道具の見落としには気づける。
  空振りには気づけない。この非対称が閾値の選び方を決めている。

## Open questions

- 突出度の閾値[dB]と、周辺中央値を取る近傍幅。合成信号で決める（人手のラベル付けは不要）。
- 倍音列判定で「有意なパワー」と見なす比率。同上。

## Out of scope

- なきかけ（precursor）の**判定**。空調・電源ハム・ファンと区別がつかない。
  突出度を測定値として表示することはするが、「危険」とは言わない。
- 能動プローブ（音を出して測る）。
- 63Hz帯の表示と検出。
- 停止後に残る履歴・サマリ・保存。
- Screen Wake Lock を保証すること、長時間運用・発熱・電池への配慮。
- EQをどれだけ切ればよいかの助言。
- EQを触れない利用者向けの対処法ガイド。
- マイクの切り替えUI。
