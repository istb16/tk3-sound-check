# Grill: トップページを機能選択ハブにし、複数機能を実装できる構造へ
Date: 2026-08-24

## Intent
ハウリングチェックを作ることが既に決まっている。その受け皿として、いま1機能しか
無いうちに複数機能前提の構造へ移す。トップページは目的ではなく通過点であり、
本命は「2機能目が素直に入る土台」。

## Constraints
- アプリは未公開で利用者は作者のみ。URL変更・後方互換の制約は無い。
- 絶対音圧(dBA)は扱えない（ブラウザはマイク感度を知らない）。ボリューム系の機能は
  すべて相対値で設計しなければならない。
- 「空振りは見落としより重い」（README の既存原則）。誤検出する道具は信用を失う。
- 分析にかけるサンプルにブラウザやコーデックの加工を通さない（audio.ts の既存原則）。
  echoCancellation / noiseSuppression / autoGainControl は全機能で false 固定。

## Key decisions
- Decision: 製品名を「サウンドチェック / Sound Check」とし、「音質チェッカー」は
  その中の1機能の名前に降格する。Reason: 3つの道具を束ねる場所の名前として
  「音質チェッカー」は誤り。リポジトリ名 `tk3-sound-check` と Firebase プロジェクト名が
  最初からこの構造を予告していた。Alternative considered: 音質チェッカーのまま。
- Decision: 実URLを持つ（`/` `/quality` `/howling` `/volume`）。history API の自作ルーター。
  Reason: 開発中に目的の機能へ直接飛べる、戻るボタンが効く、document.title を
  ルートごとに出せる。Firebase Hosting の `**` → `/index.html` rewrite が既にあるので
  追加コストは無い。Alternative considered: App.svelte 内の状態で画面を出し分ける方式。
- Decision: GA へのルート別ページビュー送信は**行わない**。Reason: 当初は
  coming soon タイルのクリックを需要計測に使う案だったが、利用者が作者のみと判明した
  時点で計測対象が存在しない。Alternative considered: 遷移ごとに手動 pageview。
- Decision: 共通化するのは (1) マイク獲得と AudioContext のライフサイクル、
  (2) 信号処理プリミティブ (signal.ts)、(3) シェル（ヘッダー・レイアウト・i18n・
  ルーティング・パネルCSS）の3層のみ。解析パイプラインと状態機械は機能ごとに独立。
  Reason: 音質チェックはバッチ（10秒録って解析して採点）、ハウリングとボリュームは
  受動リアルタイム（終わりが無い・点数が無い）。同じ状態機械に乗せると両方が歪む。
- Decision: VuMeter / RadarChart / ScoreBreakdown / VerdictPanel は音質チェック専用として
  features/quality/ 配下に置き、共通コンポーネント置き場には出さない。Reason: 他機能から
  使えないものが共通の棚に並ぶと、次に作る人が「共通だから使うべきか」で迷う。
- Decision: 「受動リアルタイムモニターの骨格」は今回**実装しない**（選択肢 X）。
  設計文書に落とすだけ。Reason: 利用者が一人もいない抽象は正しさを検証できず、
  半年後にハウリングを書き始めた瞬間に「合っていない」と分かる最悪の順番になる。
  ハウリング実装時に利用者が揃ってから切り出す。Alternative considered: 骨格を検証する
  最も安い方法としてボリュームチェック（実質 rms を100msごとに出すだけ）を先に実装する案(Y)。
- Decision: i18n は機能ごとのファイルに分割し、265行の共有 Translations 型を廃止する。
  Reason: 新機能が共有型に手を入れずに自分の文言を足せる形が「拡張できる」の実体。
- Decision: 既存テストは QualityCheck コンポーネントを直接 mount する形に張り替え、
  テスト本体（検証内容）は変更しない。Reason: 移設で音質チェックの挙動が変わっていない
  ことを既存テストがそのまま証明する。Alternative considered: App から毎回メニューを
  クリックして入る形（全テストがメニューに依存する）。
- Decision: ハウリングチェックは「鳴っているハウリング」の検出でよい。なきかけ
  （precursor）の検出は行わない。Reason: 検出は単純になり誤検出の問題が消える。
  価値は警告ではなく**周波数の特定**にある——鳴っていることは全員が分かるが、
  3.2kHz か 4.5kHz かは人間の耳では区別できない。
- Decision: ハウリングの出力はオクターブバンド名を主、Hz 数値を併記。Reason: 固定バンドの
  グライコしか無い現場でも意味が通り、かつパラメトリックEQがあるなら数値も使える。
  併記のコストはほぼゼロ。既存の signal.ts の bandPowers がそのまま使える。
- Decision: ボリュームチェックは「リアルタイム入力レベルメーター」。Reason: 音質チェックの
  音量軸との重複を避けるための唯一成立する定義。Alternative considered: 送信レベル確認
  （既存の音量軸とほぼ同じ）、部屋に対する再生音量の適正判定（dBA が要るため原理的に不可能）。
- Decision: ヘッダーに常時小さく製品名を出し、それ自体を戻る手段にする。専用の
  戻るボタンは置かない。Reason: 押せる場所が2つあるとどちらを押すか迷う。

## Surfaced assumptions
- ハウリングチェックは受動リスナー（ツール自身は音を出さない）。能動プローブは、
  端末の内蔵スピーカーが会議室のPAではないため現場の問題を説明せず、かつ AEC を
  切ったまま自分で音を出すのでツール自体が本物のハウリングを起こしうる。
- リアルタイム系の機能に「結果画面」は無い。出力は点数ではなく状態で、止めたときに
  何も残さない（サマリ・履歴・保存は作らない）。
- 表示用の短期履歴（判定に必要な数フレーム）と、終了時サマリ用の長期履歴は別物。
  前者は必要、後者は作らない。
- audio.ts の setupRawCapture（ゲイン0で destination に繋いで process を駆動する仕掛け）は
  既にチャンクを main thread へ流し続ける形なので、溜め込みをやめればストリーミング解析に
  そのまま転用できる。リアルタイム骨格の実体はここになる。
- src/counter.ts / src/style.css(296行・未 import) / src/assets/hero.png / typescript.svg /
  vite.svg は Vite テンプレートの残骸で未使用。

## Open questions
- ハウリングチェックの実装時期。設計文書のみを残し、着手時に骨格を切り出す。
- ボリュームチェックを実装するかどうか。骨格の検証手段としては最も安いが、今回は保留。

## Out of scope
- ハウリング／ボリュームのコード実装（設計文書のみ）。
- 「受動リアルタイムモニター」の共通骨格の実装。
- AudioAnalyzer / estimators / scores / provenance の分析層への変更（挙動を一切変えない）。
- ルート別の GA 計測。
- リアルタイム機能の履歴保存・結果サマリ。
