# Grill: 音質・音量判定の精度向上
Date: 2026-08-24

## Intent
一般ユーザーが、アップロードまたはマイク録音した音声から「**会議の録音環境としてどのレベルか**」を客観的に判定できるようにする。
そのうえで、「精度が上がった」を自分の主観ではなく数値で言える状態を作る。ただし自分では一切ラベル付けをしない。

## Constraints
- **自分で音声にラベル付けはしない。** 正解は外部（規格・公開コーパス・学習済みモデル）から借りる
- **公開コーパスをgitに入れない。** gitに入るのは取得スクリプト・劣化パラメータのマニフェスト・検証レポートのみ
- 一般ユーザー向け。騒音計などの計測器の所持を前提にできない
- バックエンドなしのブラウザSPA（Svelte 5 + Vite）

## Key decisions

- **決定: v1は会議音声に絞り、歌・音楽は対象外。**
  理由: ラベル付けを避ける前提では正解を外部から借りるしかなく、無参照の音声品質推定モデル（DNSMOS / NISQA / ITU-T P.563）はすべて音声専用で、歌には妥当性がない。歌を含めた瞬間、ラベルなしで客観性を担保する道が消える。
  却下案: モード切替（会議/音楽）で軸と閾値を差し替える。歌モードの正解データがどこからも借りられないため不成立。

- **決定: 学習済みモデル（DNSMOS）は製品に載せず、開発時の検証オラクルとして使う。**
  理由: ラベル付け不要／製品の判定理由は説明可能なまま／それでも精度向上を数値（順位相関）で示せる、を同時に満たす唯一の構成。
  却下案: 判定を丸ごとモデルに委ねる。説明可能性とアドバイス機能が失われる。

- **決定: 既知の物理量を注入する自己検証を導入する。**
  既知SNR・既知RT60のインパルス応答・既知クリップ率を注入し、推定値が元の値を復元できるかで**推定誤差**を測る。
  理由: 現行 `AudioAnalyzer.test.ts` は「サイン波は高得点、スクエア波は低得点」という順序しか検証しておらず、誤差が測れない。この方式は算数なのでラベル付けが発生しない。

- **決定: 絶対音圧（dBA）表示とキャリブレーションを行わない。**
  理由: 一般ユーザーが完遂できる方式は「会話音量を基準にした推定」だけで誤差±10dB。図書館(30dBA)と騒がしいオフィス(50dBA)を区別できない数字は、SNRという正確な相対値より劣る。加えてOSの入力音量スライダーはブラウザから見えないため、キャリブレーション値は黙って無効化される。
  代替: 規格の閾値への接続は絶対音圧なしで達成できる（ITU-T P.56 有効音声レベル / ISO 9921 STI / ISO 3382 残響時間）。
  却下案: スピーカー再生によるループバック校正。スピーカー出力音圧が未知で未知数2つに式1つ、原理的に解けない。

- **決定: 残響（RT60）を評価軸に戻す。**
  理由: 会議環境の音の悪さの主要因は ①暗騒音 ②残響 ③マイク設定。現行4軸は ① `noise`、③ `clip`/`volume`、`frequency` がマイク距離と特性で、**②が完全に空白**。残響は「静かな部屋なのに聞き取りにくい」の主犯であり、かつユーザーが対処可能（カーテン、カーペット、マイクを近づける）なのでアドバイス機能と相性が良い。
  なお7月の `1bba5df` で残響・エコーが外されたのはユーザーの意図した判断ではなかった。

- **決定: 残響推定は旧実装方式を採らず、発話オフセットの減衰率分布（decay-rate distribution）で行う。**
  理由: 旧 `calcReverbScore` は録音全体の最大ピーク1点からの減衰しか見ておらず、①話者の自然な減衰と部屋の残響を区別できない ②たまたま最大だった1箇所の当たり外れで結果が変わり再現性がない。

- **決定: 話し方の2軸（計14点）を削除し、その配点を残響軸に回す。**
  対象: `calcVolumeScore` のダイナミクス評価(8点)「声量にムラがある」、`calcNoiseScore` の無音区間評価(6点)「無音が長すぎる/息継ぎがない」。
  理由: 録音環境の評価に話者の喋り方は含まれない。全体100点の14%が目的外の採点になっていた。

- **決定: 処理済み・圧縮済み音声は、警告を出しつつスコアも表示する（選択肢B）。**
  理由: 一般ユーザーはZoom/Teams録音を主要導線として投げてくる。スコアが1つも出ない体験は許容できない。
  却下案: C（測定可能な軸のみ表示し、残りを「測定不能」と明示）。客観性の一貫性ではCが上だが、体験を優先した。
  **残存リスク（本人合意済み）**: ユーザーが警告を読まず、騒がしい部屋を「静かです」と信じる可能性。緩和策として警告はフッターではなく該当軸に直接バッジ表示する。

- **決定: マイク録音時、ブラウザのDSPを明示的に全てOFFにする。**
  `getUserMedia({ audio: { echoCancellation: false, noiseSuppression: false, autoGainControl: false } })`
  理由: 現行の `{ audio: true }` はChromeデフォルトで3つ全てON。「静かな環境か」を測るのにブラウザが先にノイズを消し、「音量が適正か」を測るのにChromeの自動ゲインの出力を測っていた。この経路の上ではDSPをいくら精緻化しても精度は上がらない。

- **決定: マイク録音画面に短い読み上げ文サンプルを出す。緩い指示も併記する。**
  理由: 現行は10秒間ただ録るだけで、無言だとSNRの分子も残響推定に必要な発話オフセットも存在しない。句読点で切れる2〜3文で発話区間と無音区間の両方を保証する。

- **決定: 出力は総合点（0〜100）＋判定メッセージの併記。**
  理由: ユーザーが知りたいのは点数ではなく「このまま会議していいのか」。総合点は要約として残し、実際の判定は閾値の合否メッセージで伝える。

## Surfaced assumptions
- 「客観的」には2種類あり、混同されていた。**環境評価**（物理量、正解データ不要、規格が基準）と**成果物評価**（知覚量、人間のMOSラベルが必須）。今回は入力が音声ファイル1本のみなので、**成果物から環境を無参照推定する**という第三の形を採る。
- 「良い音のサンプルを提供できない」は「正解データが存在しない」とは別。避けたいのは**自分でラベル付けする手間**であって、外部の正解を借りることは許容される。
- ノイズ軸は永久に相対値（SNR）でしか語れない。「静かな部屋か」ではなく「声に対してノイズが十分小さいか」しか言えない。

## 発見済みの実装欠陥（精度に直結）
- **帯域制限音声が周波数バランス満点を取る。** `calcFrequencyScore` は各帯域比率を `totalEnergy`（0〜ナイキスト）で割る。8kHzサンプリングや低ビットレート圧縮音声では4kHz以上にエネルギーがなく、`presenceRatio` が0.6超→明瞭度16点満点、`highEnergy`=0→キンキン判定6点満点、低音比率も小さく8点満点で**合計30点満点**。帯域を削るほどスコアが上がる。
- **`decodeFile` が元の帯域情報を破棄する。** `new OfflineAudioContext(1, 1, 44100)` により `decodeAudioData` が44100へリサンプルするため、ファイル入力では `audioBuffer.sampleRate` が常に44100。元が8kHzだったか48kHzだったか判別不能。帯域上限はスペクトルロールオフの実測で得るしかない。
- **音量判定が全体RMSベース。** 無音区間を含めた全体RMSなので、間の多い録音は音量が低いと誤判定される。ITU-T P.56 の有効音声レベル（発話区間のみ）に置き換えるべき。
- **マイク経路のブラウザDSPが全てON**（上記「決定」参照）。

## 実測結果（実音声4話者 × 16kHz/48kHz・2026-08-24）

素材は **CMU ARCTIC 4話者**（slt=米女性 / bdl=米男性 / ksp=インド英語男性 /
awb=スコットランド英語男性）を話者ごとに連結して4素材。それを
**16kHzと48kHzの両方**に変換して8素材・240条件。詳細は `validation/report.md`。

| 推定対象 | 件数 | バイアス | MAE | 最大誤差 |
|---|---:|---:|---:|---:|
| 帯域上限[Hz] | 24 | -8.3 | 8.3 | 100 |
| 1kHz以上の傾斜[dB/oct] | 32 | -0.37 | 0.78 | 2.99 |
| 有効音声レベル[dBFS] | 56 | 0 | 0 | 0 |
| クリップ率 | 32 | 0 | 0 | 0 |
| SNR[dB] | 128 | +0.08 | 1.62 | 5.38 |
| RT60[秒] | 43 | -0.067 | 0.141 | 0.515 |

単調性はすべて想定どおり（snr→noise +0.999 / clip→clip -0.949 /
cutoff→frequency **+1.0** / rt60→reverb -0.931 / rt60→noise -0.412 だが効果量2.25/25点）。

### 48kHzでの検証（製品のマイク録音のレート）

推定器の定数はすべて秒/Hzで書いてあるが、**FFT長だけは2048固定**なので
周波数分解能がサンプルレートに反比例する（16kHz:7.8Hz/bin → 48kHz:23.4Hz/bin）。
帯域上限の検出は100Hz幅の帯で見るので、48kHzでは1帯あたり4binしか入らない。
ここが壊れていないかを実素材で確かめた。

**結果: 素材ごとの誤差が両レートでほぼ一致した。** SNRのバイアスの差は
0.2dB以内、RT60は0.04秒以内。48kHzで新しい誤差は出ていない。

| 話者 | SNRバイアス 16k / 48k | RT60バイアス 16k / 48k |
|---|---|---|
| awb | +1.99 / +2.04 dB | +0.018 / -0.017 秒 |
| bdl | +0.31 / +0.38 dB | +0.043 / +0.008 秒 |
| ksp | +0.53 / +0.44 dB | -0.027 / -0.033 秒 |
| slt | +0.74 / +0.92 dB | -0.108 / -0.096 秒 |

**測れることが増えた点**: 16kHz素材ではナイキストが8kHzなので、素材そのものの
帯域上限は原理的に検出できない（120行中87行が「加工痕跡なし」）。48kHzに上げると
素材の実際の上限7.2kHzを95/120行で検出する。製品は48kHzで録るので、
Zoom/Teams を通した音（8kHz以下しか中身が無い）は実際に検出できる側にある。

残る13行はすべてクリッピング条件で、これは正しい。クリッピングは非線形なので
全帯域に高調波を生む——0.02%のクリップでも7.2kHz以上が埋まり、帯域制限は消える。

**この検証の限界を明記する。** 16kHz素材を48kHzに上げても8kHz以上に中身は
生まれない。したがってこれは「48kHzで実装が正しく動くか」の検証であって、
「8kHz以上に本物の中身がある録音で正しいか」の検証ではない。
8/11/16kHzのカットオフ条件は依然として試せていない（広帯域の実素材が必要）。

### SNRの系統的な楽観を分子と分母に分解した

バイアス +0.96dB の内訳を「分子（発話パワー）」と「分母（ノイズパワー）」に
分けて測ると、原因が領域ごとに違っていた。

| 注入SNR | 合計誤差 | 分子 | 分母 | ノイズ用フレーム数 |
|---|---:|---:|---:|---:|
| 0dB | +1.53 | +0.01 | **-1.52** | **0** |
| 5dB | +1.43 | +2.50 | +1.06 | 309 |
| 10dB | +0.55 | +2.10 | +1.55 | 205 |
| 20dB | -0.57 | +1.25 | +1.82 | 50 |
| 30dB | +1.42 | +0.15 | -1.27 | 47 |

**0dB では無音フレームが1つも取れていなかった。** 有音/無音の2群分離が
棄却され、固定閾値(p95-25dB)も分布の下端に届かず、全フレームが有音扱いになる。
そこで代替として全フレームの第2パーセンタイルを使っていたが、これは標本の
最小値に近いので系統的に低く出る——ノイズを -1.52dB 過小評価し、SNRを
**+1.53dB 楽観的に**読んでいた。一番騒がしい録音を「そこまで悪くない」と
言う方向の誤りで、製品の目的からすると一番許容できない向き。

棄却理由を特定すると、落ちていたのは**2群の間隔の条件だけ**だった
（間隔4.35dB < 閾値6dB）。下側の群の標準偏差は1.03dBで、定常雑音そのもの。

#### 試して外れた仮説: 間隔の閾値を緩める

「実際の無音フレームを使えるようにするほうが筋が良い」と考えて閾値を
6→4.5→3.5→3 と振ったが、**すべて悪化した**（バイアス 0.956 → 1.093）。
分離を通すと有音側が大きい声に偏り、分子が余計に膨らむため。
筋の良さではなく実測で決めた。

#### 採用: 代替パーセンタイルを p2 → p20

この領域はほぼ全フレームが雑音支配なので、下端の極値ではなく分布の下寄りの
水準を取るほうが素直。p2〜p35 を実コードパスで走査した結果:

| 代替 | 全体バイアス | 全体MAE |
|---|---:|---:|
| p2（従来） | +0.956 | 1.665 |
| **p20** | **+0.707** | **1.539** |
| p25 | +0.655 | 1.545 |
| p30 | +0.592 | 1.596 |
| p35 | +0.525 | 1.662 |

MAE最小の p20 を採った。SNR 0dB の誤差が **+1.53 → -0.46dB**（楽観から安全側）。

なお 5〜20dB に残る分子 +1.2〜+2.5dB は、2群分離の境界が発話分布の内側に
来るため有音側が大きい声に偏ることによる。分母の同方向の偏りとほぼ打ち消し合って
合計誤差は小さい。低SNRでは無音と小さい声が原理的に区別できないので、ここを
これ以上追うと素材への過適合になる。追わない判断をした。

### 見つけたが直せなかった限界: 無音区間の無い録音

素材から間を取り除いて（無音区間ゼロの）最悪ケースを作ると、2群分離は
**成功してしまい**、「小さい声」をノイズフロアとして報告する。結果SNRを
25〜48dB低く読む——静かな部屋を騒がしいと言う向きの誤り。

検出できないか試した仮説: **本物の無音は連続する**（息継ぎは100〜500ms）ので、
無音と分類されたフレームの連続長で判別できるはず。**外れた。**

| 素材 | 連続長 中央値 | 最大 |
|---|---:|---:|
| 通常（無音あり） | 2〜6 | 9〜78 |
| 間を除去（無音なし） | 2〜3 | 10〜25 |

完全に重なる。20msフレームでは実音声の語間も2〜3フレームしかないため。
**録音に背景雑音だけの区間が1つも無ければ、SNRは原理的に測れない。**
これは推定器の欠陥ではなく情報の不足で、しかも信号から検出できない。

実害の見込みは低い（10秒の自然な発話に40ms以上の切れ目が1つも無いことは
実素材では観測されなかった。上の最悪ケースは人為的にフレームを削って作った）。
直せない限界として記録し、対策は入れていない。スペクトルの定常性で判別する
手はあるが、実害が確認できていない対策にフレームごとのFFTを追加する判断は保留。

### マイク位置ごとの測定能力を押さえ、近似開始点の過適合を直した（2026-08-24）

#### 1. マイク位置ごとの残響の測定能力

RT60を0.6秒に固定してDRRだけを振った条件（レポートの「マイク位置ごとの残響の
測定能力」節）。近似の開始点を -8dB にした状態の実測:

| DRR | 目安 | 測定できた | バイアス[秒] | MAE[秒] | イベント数 | 参考値扱い |
|---:|---|---:|---:|---:|---:|---:|
| +20 dB | 近接(10〜30cm) | 8/8 | -0.243 | 0.253 | 4.3 | 3/8 |
| +15 dB | 近接 | 8/8 | -0.178 | 0.182 | 5.5 | 1/8 |
| +10 dB | 卓上・ノートPC | 8/8 | -0.054 | 0.101 | 5.9 | 1/8 |
| +5 dB | 卓上 | 7/8 | +0.085 | 0.098 | 3.9 | 4/8 |
| 0 dB | 部屋の向こう | 7/8 | +0.137 | 0.144 | 3.5 | 5/8 |
| -10 dB | かなり遠い | 5/8 | +0.182 | 0.182 | 2.5 | 6/8 |

**動作範囲は DRR +5〜+15dB（MAE 0.10〜0.18秒）。** ここは卓上・ノートPCのマイクの
範囲で、この道具の主用途に一致する。その外では ±0.18〜0.24秒のバイアスが出る。
近接マイクでは過小評価（観測できる減衰が浅い）、遠いマイクでは過大評価になる。

**48条件のうち20件が参考値として開示される。** 減衰イベントが4件未満だと信頼
しないという判定が、実際に高い頻度で働いている。残響軸が確定値を出せるのは
限られた条件だけ——これは欠陥ではなく、無参照でRT60を測ることの限界の開示。

DRRを盲目的に推定してバイアスを補正する手はあるが、DRRの無参照推定は難問で、
素材に合わせた補正係数を入れる誤りを一度やっている（削除した1.35）。やらない。

#### 2. 近似開始点を単一のDRRで決めていた（過適合）

前回 -10dB を選んだが、**RT60を振る条件はすべて既定のDRR(+10dB)で生成される**ので、
それは最適化した点そのものでの評価だった。DRRを振った条件で見ると答えが変わる:

| 開始点 | rt60条件のMAE | DRR全域 測定 | DRR平均MAE | 最大バイアス | 参考値 |
|---|---:|---:|---:|---:|---:|
| -6dB | 0.170 | 48/48 | 0.183 | 0.290 | 10/48 |
| **-8dB** | 0.141 | **43/48** | **0.160** | **0.243** | 20/48 |
| -10dB | **0.096** | 40/48 | 0.174 | 0.242 | 31/48 |
| -12dB | 0.118 | 35/48 | 0.181 | 0.324 | 41/48 |
| -14dB | 0.109 | 20/48 | 0.176 | 0.266 | 47/48 |

-8dB に変更。**削除した補正係数1.35と同じ誤りを繰り返しかけていた**——一点で最良の
値を選んで全体を悪くする。単一条件で決めた定数は、その条件を振れるようになった
時点で必ず見直す。

副産物としてSNRのバイアスがほぼ消えた（+0.71 → +0.078dB）。残響ガードに渡す
RT60の推定が改善したため。

#### 3. rt60 → noise の結合は対処不要と判定した

DRRを現実的にしたあと ρ が -0.218 → -0.625 に強まったが、**効果量は 0.75/25点(3%)**
で効果量ゲート(10%)を下回る。ノイズ軸はRT60 0.7秒まで25.00点のままで、1.0秒で
24.25点。ρが強まったのはわずかな動きが一貫して順序づいただけ。

| RT60 | ノイズ軸/25 |
|---:|---:|
| 0.2〜0.7秒 | 25.00 |
| 1.0秒 | 24.25 |
| 1.5秒 | 24.38 |

スケールフリーな相関に釣られてSNR精度を犠牲にしかけた過去があり、そのために
効果量ゲートを入れた。今回はそれが正しく働いた事例。

#### 4. 配点と判定の検証も改善した（副産物）

複合条件も現実的なDRRで生成されるようになり、MOSがモデルの弁別できる範囲に入った。

| | 以前（湿った条件） | 現在 |
|---|---|---|
| 判定のMOS平均 good/usable/poor | 1.97 / 1.56 / 1.49 | **2.79 / 2.56 / 2.21** |
| 配点の相関（ノイズと残響だけの群） | 0.800 | **0.859** |

判定の3段階がMOSの上で明確に分離した。配点の候補間の差も広がったが
（現行0.859 / ノイズ寄せ0.929）、**これを根拠に配点を変えない。**
DRR +10dB では残響の劣化が軽くなるので、条件表のSNR側とRT60側で知覚的な振れ幅が
揃っていない。「ノイズ寄せが良い」はその不均衡を反映している可能性が高く、
条件の選び方に合わせて配点を決めることになる。知覚的に釣り合った条件表を
作るのが先だが、それをオラクルで作ってオラクルで検証すると循環する。
### 残響の検証がすべて非現実的に湿った素材で行われていた（2026-08-24）

「直接音対残響比(DRR)を要因として振る」を実行した。RT60は部屋の性質だが、マイクに
届く残響の量はマイク位置で決まる。検証基盤はこれを振幅比 0.45 に固定していた。

#### まず条件の作り方を間違えた

振幅比 0.15〜1.0 で振って測ったところ、推定RT60は 0.55〜0.64秒で動かず、
残響軸も MOS も反応しなかった（どちらも ρ≈-0.07）。「マイク位置は影響しない」と
結論しかけたが、**真のDRRを計算したら -9.6〜-26dB だった。**

振幅比では駄目だった。直接音は先頭1サンプル、残響は数千サンプルの積分なので、
同じ振幅比でもRT60によってDRRが変わる。旧既定(0.45)の実測値:

| RT60 | DRR |
|---:|---:|
| 0.2秒 | -11.9 dB |
| 0.6秒 | -16.6 dB |
| 1.5秒 | -20.6 dB |

実際の録音のDRRはこのあたり:

| マイク位置 | DRR |
|---|---|
| 近接(10〜30cm) | +15 〜 +25 dB |
| 卓上・ノートPC(50cm〜1m) | +5 〜 +15 dB |
| 部屋の向こう(2〜3m) | -5 〜 +5 dB |

**つまり検証基盤の全条件が「大聖堂並み」の湿り方で、しかもRT60が長いほど湿るという
交絡まで入っていた。** DRRを物理量で指定して合成する方式に変えた（目標値に対して
実測が0.00dB一致）。

#### 現実的なDRRにすると残響の精度が崩れた

既定を卓上マイク相当(+10dB)にして測り直した結果:

| | 旧（DRR -12〜-21dB） | 新（DRR +10dB） |
|---|---:|---:|
| RT60 バイアス | -0.019 秒 | **-0.353 秒** |
| RT60 MAE | 0.067 秒 | **0.361 秒** |
| rt60→reverb ρ | -0.945 | -0.75 |
| rt60→noise ρ | -0.218 | -0.61 |
| drr→reverb ρ | -0.069（無反応） | **+0.912** |

**残響の精度に関する過去の数値はすべてこの条件で測ったものだった。**

原因は物理的に明確。発話が止まった直後の下降は部屋の残響ではなく発話自体の
立ち下がりで、直接音が残響より下がるまで待たないと発話の傾き（急）を測ってしまう。
待つ量はDRRで決まる。DRRが -17dB なら残響が最初から大きいので待つ必要がなく、
3dBで十分だった。+10dB では10dB下がるまで待つ必要がある。

#### 補正係数1.35は誤った校正だった

「発話を通して観測した減衰は部屋のRT60より緩く出る」として1.35で割り戻していたが、
**その校正は湿った素材で行われたもの**で、現実的なDRRでは逆に過小評価になる。
補正を残すと悪化した。削除した。

| 補正 | 近似開始 | バイアス | MAE | n |
|---|---|---:|---:|---:|
| 1.35 | -3dB | -0.353 | 0.361 | 48 |
| 1.35 | -12dB | -0.076 | 0.123 | 32 |
| なし | -3dB | -0.229 | 0.260 | 48 |
| なし | -6dB | -0.126 | 0.170 | 46 |
| なし | -8dB | -0.067 | 0.141 | 43 |
| **なし** | **-10dB** | **-0.001** | **0.096** | 40 |
| なし | -12dB | +0.086 | 0.118 | 32 |

補正を削除し、近似の開始点を -3dB → -10dB にした。単調性も -0.937 で最良。
深く待つほど測定できる条件が減る（48→40件、減るのはRT60 0.7秒以上）が、

#### 残響軸はマイク位置に応じて動くようになった

| DRR | 残響軸/20 |
|---:|---:|
| +20 dB（近接） | 18.6 |
| +15 dB | 18.1 |
| +10 dB（卓上） | 15.8 |
| +5 dB | 12.8 |
| 0 dB（部屋の向こう） | 9.8 |

これは欠陥ではなく正しい挙動。この道具が答えるのは「この録音は会議に使えるか」

一方、**スマホ録音のRT60 0.23秒を「近接マイクだから短く出た」と説明したのは

### 可逆WAVで帯域上限の検出が壊れていたことが分かった（2026-08-24）

44.1kHz 可逆の WAV（Windows標準アプリで録音）を追加してもらった。まず素材そのものの
性質:

| 周波数 | ピーク基準レベル |
|---:|---:|
| 7000〜8000Hz | -39 〜 -44 dB |
| 8500Hz | -54 dB |
| 9000Hz | -76 dB |
| 9400Hz以上 | -84 dB（床） |

**44.1kHz可逆でも8.5kHz以上に中身が無い。** Windowsの音声処理パイプラインが内部で
16kHzに落としていると見られる。つまり「可逆形式で録れば広帯域」ではない。
広帯域の穴は形式では埋まらない。

#### 検出器はこの明白な崖を見逃していた

落差 20.1dB と報告し、閾値25dBに届かないので帯域上限をナイキスト(22050Hz)と
判定していた。**8kHz帯域の音声を「帯域制限なし」と報告していた。**

原因は窓幅が500Hz固定だったこと。遷移幅が経路で大きく違う。

| 経路 | 遷移幅 |
|---|---|
| 合成した帯域制限（1023タップFIR） | 約200Hz |
| 実録音（Windowsの処理経由） | 約1000Hz |

500Hzの窓は後者の遷移域をまたぐので落差を過小評価する。窓幅を変えると同じ信号で
20.1dB → 29.9dB(1000Hz窓) → 35.0dB(1500Hz窓) と出る。同じことが実録音のAAC
（22.5dB）でも起きていた。**2件とも閾値の直下という偏りは偶然ではなかった。**

複数の窓幅(500/1000/1500Hz)で走査し、**閾値を超えた最も狭い窓**を採るようにした。
最も深い落差を採ると急峻な崖でも常に最大幅の窓が勝ってしまい、境界の局在性が落ちる。

窓を広げても自然なロールオフを崖と誤検出する危険は増えない。8kHz付近では1オクターブが
8kHz幅なので、1500Hzの窓対（計3000Hz）で見える自然な落差は -12dB/oct でも3〜4dB。

#### 境界の定義を2回間違えた

遷移幅が5倍違うので、境界を「形」で決める旧方式（隣接バンドの落差が8dBを超える間
下る）は経路ごとにずれる。実録音では落差が緩やかすぎて詰めが早期に止まり、遷移域の
中ほど(8700Hz)を返していた。

**1回目の誤り: 「通過域の平均から-6dB」。** 音声のスペクトルは通過域内でも
-6〜-12dB/oct で落ちているので、平均を基準にすると基準が高く出て境界が下にずれる。
-12dB/oct の信号の 3400Hz カットオフを **2300Hz**（-1100Hz）と報告した。

**2回目の誤り: 窓の選び方。** 通過域の傾きを外挿する方式に直したが、最大落差で窓を
選んでいたため常に1500Hz窓が勝ち、近似区間が遷移域から1500Hz離れて局所の傾きを
拾えなかった（近似区間の長さを3倍にしても結果が1Hzも変わらないという不自然さで
気づいた）。狭い窓を優先する方式に直して解決。

#### 判定点は実測で -6dB を選んだ（-8dBのほうが合成条件では正確）

| 判定点 | 合成条件の誤差 | 実録音の帯域上限 | band-limited警告 |
|---|---|---|---|
| **-6dB** | MAE 8.3Hz / 最大100Hz | **8000〜8100Hz** | **出る** |
| -8dB | 0Hz | 8300Hz | 出ない |

-8dB は合成条件の誤差を完全に0にするが、16kHz由来の音声を「帯域制限なし」と
報告することになり、この検出器が存在する目的を損なう。合成条件の100Hz（1バンド）は
周波数軸のスコアを0.04点動かすだけで実害が無い。-6dB は振幅半減点として標準的な
定義でもあり、独立した根拠がある。

#### 警告の閾値に余裕を持たせた（8000 → 8500Hz）

実測した上限は8000ちょうどには来ない。リサンプラのフィルタ形状で±100〜200Hzずれ、
実録音3本では 8000〜8100Hz に散った。8000を閾値にすると 8100Hz の16kHz由来音声を
取りこぼす（実際に起きた）。次の意味のある区切り（11kHz以上の中身）までは十分
距離があるので、余裕を持たせても誤検出は増えない。

#### 直した結果（実録音3本）

| ファイル | 帯域上限 | 加工痕跡 | 判定 | 参考値扱いの軸 |
|---|---:|---|---|---|
| PC (m4a) | 8100Hz | band-limited, digital-silence, zero-run | usable / 未確定 | noise, reverb, frequency |
| PC (wav) | 8100Hz | band-limited, digital-silence | usable | noise, reverb, frequency |
| スマホ (m4a) | 16000Hz | なし | **good** | なし |

PCの2本はどちらも「8kHz帯域・ノイズ抑制あり」と正しく判定され、スコアを確定値として
出さない。スマホの1本だけが確定した「良好」になる。

**この一連の欠陥は実録音でしか見つからなかった。** 合成した帯域制限はFIRが急峻すぎて
500Hz窓でも通ってしまい、24条件すべて誤差0Hzで「完璧」に見えていた。
### 実録音を入れて初めて分かったこと（2026-08-24）

`fixtures/real/` に実録音2本（PCとスマホ、どちらもm4a/AAC）を置いて、製品と同じ
復号経路（`decodeAudioData`）で解析した。Node の検証基盤は WAV しか読めないので、
ブラウザで走るテスト `src/lib/real-material.test.ts` から実行する。素材が無ければ
黙って通るので、素材を git に入れなくても検証は成立する。

#### 音量軸の理想帯域が制作目標であって適否の基準ではなかった

**両方の録音が音量軸だけで「不可」判定になっていた。**

| | 有効音声レベル | 音量軸(旧) | 判定(旧) |
|---|---:|---:|---|
| PC録音 | -31.4 dBFS | 1/15 | poor（最弱=volume） |
| スマホ録音 | -26.2 dBFS | 7/15 | poor（最弱=volume） |

理想帯域 -20〜-14dBFS は放送・配信の**制作目標**であって、録音が使えるかの基準では
ない。実害はどこにも無かった（SNRは20.9dBと32.7dB、音割れゼロ）。

公表されている発話レベルの基準はいずれももっと低い。

| 出典 | レベル |
|---|---|
| ITU-T P.56 系の試験手順 | 有効音声レベルを **-26 dBov** に正規化 |
| EBU R128 / ATSC A/85 | 番組ラウドネス目標 -23 LUFS / -24 LKFS |
| 民生の録音アプリ・会議端末 | おおむね -30〜-18 dBFS |

帯域を **-30〜-12 dBFS** に広げた。下限の根拠は、16bitでも -30dBFS から量子化フロア
(-96dBFS)まで65dBの余裕があり実害が出ないこと。上限は発話の波高率12〜18dBから、
これ以上ではピークが0dBFSに達しはじめること（実際に割れているかは音割れ軸が測る）。

この軸は品質の尺度ではなく**衛生チェック**だと位置づけを変えた。レベルは後から
正規化できるし、録音環境について何も語らない。

#### 直した結果

| | 総合 | 判定 | 参考値 | 加工痕跡 |
|---|---:|---|---|---|
| PC録音 | 98/100 | usable / **未確定** | noise, reverb | digital-silence, zero-run |
| スマホ録音 | 96/100 | **good** | なし | なし |

#### 加工痕跡の検出が実素材で機能した

PCの録音は**無音区間のフロアが -104.8 dBFS、完全なゼロが 312.7ms 連続**していた。
ノイズ抑制ゲートの痕跡として一義的で、`digital-silence` と `zero-run` の両方が
発火した。結果ノイズ軸と残響軸が参考値になり、判定は「未確定」になる。

これは正しい。ゲートがかかった音声のSNR 32.7dB と RT60 0.13秒はどちらも
実際より良い値で、そこから録音環境を推定することはできない。
**この判定閾値は合成信号でしか検証できていなかったので、実素材での初めての確認。**

スマホの録音は無音フロア -49.4 dBFS・ゼロ連続なしで、ゲートはかかっていない。
実際の部屋のノイズフロアが素直に残っている。こちらは痕跡なしと判定した。

#### 録音条件を確認した — ゲートは既定の経路で起きる

PCの録音は **Windows標準のサウンドレコーダー**、スマホの録音は **6畳ほどの部屋で
マイクに近め**という回答だった。ここから2つ分かった。

**(a) 加工痕跡は例外ではなく既定の経路で起きる。**
Windows利用者が音声を録る最も自然な手段が、ノイズ抑制ゲートのかかった音声を生む。
「まれに加工済みファイルが来る」ではなく「素直に録るとまず加工されている」が実態。
したがってこの警告経路は主要な経路として扱う必要がある。

**(b) その結果、案内の文面が手詰まりになっていた。**
警告の導入文は「環境を正確に測るには、このツールのマイク録音を使ってください」だった。
ところが Windows の「オーディオの拡張機能」はドライバ層で効くので、`getUserMedia` の
制約（`echoCancellation: false` など）では切れない。**このツールで録音しても同じ
ゲートがかかる可能性がある**ので、そのときこの案内は「いまやったことをやれ」に
なってしまう。

経路（ファイル / マイク）を覚えて案内を分けた。マイク経路では OS 側の設定
（サウンドの設定 → 入力デバイスのプロパティ → オーディオの拡張機能をオフ）を案内する。

検出そのものは両経路に等しく効いている（`analyzeSamples` が常に `detectProvenance` を
呼ぶ）ので、設計は元から正直だった。壊れていたのは次の一手の案内だけ。

**(c) スマホ録音のRT60 0.23秒は妥当だが下限値。**
6畳の家具のある部屋の残響時間は一般に0.3〜0.5秒。実測0.23秒はやや乾いた側だが、
「マイクに近め」なら直接音が支配的になり、観測できる減衰は部屋の応答より短く出る。
直接音対残響比が効くという既知の交絡と一致する。**この値は部屋のRT60の下限として
読むべきで、部屋の値そのものではない。** 残響軸の閾値をこの基盤で較正できない
理由がここにも現れている。
#### 8kHz以上のカットオフ検出が実素材で確認できた

長く残っていた穴（合成信号でしか8kHz超を試せていない）に実素材が答えた。
**スマホ録音の 16000Hz のコーデックカットオフを、落差 34.1dB で検出した。**
合成でも上げ変換でもない、民生機材の実録音である。

PC録音のほうは落差 22.5dB で閾値(25dB)に届かず、帯域上限はナイキスト(22050Hz)と
報告した。高ビットレートAACのカットオフ（19〜20kHz付近）を取り逃がしている。
判定に影響は無い（どちらも7kHz以上で帯域幅は満点）が、閾値が高ビットレート
コーデックに対して際どいことは記録しておく。

#### 音量軸にも検証条件が無かった

周波数軸で見つけたのと同じ穴だった。素材を -17dBFS に正規化しているので、
音量軸は常に満点で検証にならない。既知レベルへスケーリングする条件を追加した。

| 要求 | 到達したレベル | 音量軸 |
|---:|---:|---:|
| -45 dBFS | -45.0 | 0/15 |
| -35 dBFS | -35.0 | 9/15 |
| -30 dBFS | -30.0 | 15/15 |
| -26 dBFS | -26.0 | 15/15 |
| -20 dBFS | -20.0 | 15/15 |
| -12 dBFS | **-16.0** | 15/15 |
| -8 dBFS | **-16.0** | 15/15 |

効果量は 15/15点（満点まで使える）、ρ=0.809。1.0にならないのは -12 と -8 が
どちらもピーク上限に当たって -16dBFS で止まり、同順位になるため。

**つまり実音声では -16dBFS より上の有効音声レベルに到達できない**（波高率のため、
それ以上に上げるとクリップする）。音量軸の上限側は原理的に試せない条件だった。

注意: level 条件の推定誤差は 0 だが、これは**独立した検証ではない**。真値の計算と
製品の推定器が同じ有音フレームの定義を使っているので、一致するのは当然。
ここで確かめられるのは「同じ定義を使っている限り一貫している」ことだけ。
### 周波数軸が声質を測っていた（2026-08-24）

配点の検証で「周波数軸の配点を下げると相関が上がる」と出続けたので、この軸に
**検証条件が1つも無い**ことに気づいた。帯域制限（カットオフ）の条件はあったが、
内訳の最大項目「明瞭度」10点が捉えるはずの**こもり**——帯域は削らずに高域だけが
緩やかに落ちる劣化——を注入する手段が無かった。

#### こもりの条件を追加した

1kHz以上を dB/oct で落とす直線位相FIRを、目標振幅特性の逆FFTから作る
（`validation/lib/degrade.ts` の `applyTilt`）。注入は正確:

| 注入 | 実測(2k→4k) |
|---:|---:|
| -3 dB/oct | -2.95 |
| -6 dB/oct | -5.90 |
| -9 dB/oct | -8.85 |
| -12 dB/oct | -11.81 |

#### 結果: 声質に14倍敏感だった

| | 値 |
|---|---|
| -12dB/oct のこもりを注入したときの周波数軸の動き | **0.5 / 25点** |
| 劣化なしでの話者間のばらつき | **7 / 25点** |

順位相関は ρ=0.835 と綺麗に出るが、効果量0.5点では意味がない。内訳を見ると
原因は明確だった。明瞭度比率（500〜3000Hz ÷ 有効帯域全体）は**分母に0〜500Hzを
含む**ので、基本周波数の低い声で構造的に下がる。

| 話者 | 明瞭度比 | 明瞭度(10点) | こもり(4点) |
|---|---:|---:|---:|
| bdl（米男性） | 0.352 | 8.8 | 4.0 |
| slt（米女性） | 0.269 | 6.7 | 4.0 |
| awb（スコットランド男性） | 0.220 | 5.5 | 4.0 |
| ksp（インド男性） | 0.135 | **3.4** | **2.2** |

ksp は48%のエネルギーが200Hz以下にあり、低い声であることで二重に減点されていた。
**低い声であることは録音環境の欠点ではない。** この道具の目的（環境の評価）から
外れている。

#### 1kHz以上のスペクトル傾斜に置き換えた

基本周波数と第1フォルマントより上だけを見るので声質の影響が小さく、しかも
**注入している物理量そのもの**なので真値と直接比べられる。

| 注入した傾き | awb | bdl | ksp | slt | 話者間の幅 |
|---:|---:|---:|---:|---:|---:|
| 劣化なし | -8.75 | -5.67 | -2.41 | -5.62 | 6.34 |
| -6 dB/oct | -14.76 | -11.81 | -8.48 | -12.11 | 6.29 |
| -12 dB/oct | -19.71 | -17.91 | -16.17 | -17.89 | 3.53 |

注入量にほぼ1:1で追随する（0→-12の注入で実測が -10.95〜-13.76 動いた）。
ksp は明瞭度比では最下位だったが傾斜では**最も平坦**——2つの尺度は話者を逆順に
並べる。明瞭度比が測っていたのが高域の欠落ではなく基本周波数への集中だったことの
裏付けになる。

内訳を「有効帯域幅 15点 + 1kHz以上の傾斜 10点」の2つだけにした。効果:

| 条件→軸 | ρ | 効果量 |
|---|---:|---:|
| tilt→frequency | 0.835 → **0.987** | 0.5 → **8 / 25点** |
| cutoff→frequency | 1.0 → 1.0 | 4.25 → **9 / 25点** |

傾斜の推定誤差も測れるようになった: **バイアス -0.37 / MAE 0.78 / 最大 2.99 dB/oct**。
測れる物理量が4つから5つに増えた。

**捨てたもの:** 「低域が過剰（こもり）」と「高域が過剰（キンキン）」の内訳。
前者は上記のとおり声質を測っていた。後者は実音声4話者で高域比が0.002〜0.015と
一度も発火せず、検証条件も無かった。傾斜の採点を両側にして、傾きが正（高域が
上昇している）ときだけ減点する形に置き換えた。境界は自然な範囲（最も平坦な観測値
-2.4dB/oct）から十分離して 0dB/oct に置いた。明るい声と明るいマイクは4話者では
分離できない。

### 踏んだ誤り: 絶対レベルの閾値で異常入力を塞ごうとした

内訳を変えたあと、100Hzの正弦波が周波数軸で満点を取ることに気づいた。崖の走査は
1500Hzから始まるので、それより上に何も無い入力では崖が見つからずナイキストを返す。
旧設計は明瞭度比率がこの穴を塞いでいた。

最初「帯域内のピークから60dB以内にある最上のバンド」で塞いだ。**これは
-12dB/oct で自然に落ちる広帯域信号（7.3オクターブで-88dB）を 3800Hz の帯域制限と
誤検出した。** `provenance.ts` の冒頭に「絶対レベルの閾値では判定できない。自然な
音声のスペクトルは1kHz以上で -6〜-12dB/oct で落ちる」と自分で書いてある、その誤り
そのものだった。既存のテストが捕まえた。

判別できるのは**形**のほう。信号が無い領域は窓関数のリーク床なのでレベルがほぼ
一定（振れ幅6dB未満）でピークから遠い（60dB超）。自然なロールオフは落ち続けるので
振れ幅が大きい。この2条件に変えて解決した。

### 傾斜が測れないときは周波数軸を参考値にする

近似区間（1〜7kHz）がスペクトルの床だったり、帯域が2kHzも無いときは傾斜が
測れない。10点分を黙って中間値で埋めるのは、残響で直したのと同じ問題なので、
その場合は周波数軸を参考値として開示するようにした。

### ノイズ軸の満点を SNR 40dB → 25dB にした

**40dBでは実質的に誰も「良好」判定に到達できなかった。** 判定は最弱の軸の達成率で
決まり「良好」は75%以上なので、40dB満点はノイズ軸だけで SNR 30dB を要求する。
劣化を一切加えていないスタジオ録音（素材自身のSNR 26.5〜32.6dB）でも4話者すべてが
「使える」止まりで、288条件を通して「良好」が1件も出ていなかった。

公表されている了解度の基準はどれもこれよりはるかに低いSNRを「良好」とする。

| 出典 | 「良好」とされるSNR |
|---|---|
| ISO 9921 | 残響が無ければ +15dB 程度で STI 0.75「良好」 |
| ANSI S12.60（教室） | 暗騒音35dBA以下 → 発話50〜55dBAで SNR 15〜20dB |
| 会議音声の一般的な指針 | 20dBで良好、15dBで許容 |

25dB満点にすると SNR 20dB→達成率0.80（良好）、15dB→0.60（使える）、
12dB→0.48（使えない）となり上の基準と一致する。25dB以上を同点にするのは、
この道具の目的にとって25dBと40dBの差が答えを変えないため。

ノイズ軸の効果量も 18.5/25点 → **25/25点** になった（満点まで使えるようになった）。

### 判定がMOSの上で分離するようになった

| 判定 | 件数 | MOS平均 |
|---|---:|---:|
| good | 5 | **1.968** |
| usable | 6 | 1.563 |
| poor | 133 | 1.488 |

以前は good が0件で、usable と poor のMOS分布がほぼ重なっていた。

ただし**16kHz素材では「良好」を出しにくい**。帯域上限が7.4kHzと実測されると
加工痕跡（band-limited）として周波数軸とノイズ軸が参考値になり、good が出ない。
これは正しい挙動（16kHzサンプリングの素材は加工済みと見なすのが妥当）だが、
判定閾値そのものの検証には48kHzの未加工素材が必要。素材の穴に戻る。
### RT60の最大誤差は乱数系列に敏感（信頼判定が受け止めている）

複合条件を追加すると生成時の乱数系列が変わり、インパルス応答の実現値も変わる。
同じ設定で3回生成したときのRT60の誤差:

| 生成 | 件数 | バイアス | MAE | 最大誤差 |
|---|---:|---:|---:|---:|
| 1回目 | 43 | -0.027 | 0.083 | 0.370 |
| 2回目 | 42 | -0.026 | 0.105 | 0.845 |
| 3回目 | 39 | -0.022 | 0.072 | 0.486 |

**バイアスとMAEは安定するが、最大誤差は倍以上ぶれる。** 最大誤差の値を単独で
読んではいけない。

重要なのは、この揺れが利用者に届いていないこと。減衰イベント4件以上（=確定値として
出す行）に絞ると:

| | 件数 | MAE | 最大誤差 |
|---|---:|---:|---:|
| 確定値として出す行 | 33 | 0.052 | **0.133** |
| 参考値として開示する行 | 6 | 0.184 | 0.486 |

最大誤差0.486秒の行はすべて参考値として開示されている。信頼判定を件数ベースに
したことがここで効いている。測定不能になった9件もすべてRT60 1.0秒以上だった。

### 軸の配点を借り物の基準で検証した（2026-08-24）

配点（ノイズ25 / 周波数25 / 残響20 / 音量15 / 音割れ15）は目的からの判断で置いた
初期値だった。自分でラベル付けはしないという制約があるので、人間の主観評価で
学習された DNSMOS を借り物の基準として使った。

#### 単独条件では配点を検証できない

「ノイズ25点・残響20点」が妥当かは、「ノイズが強い録音」と「残響が長い録音」の
どちらを低く評価すべきかという比較でしか問えない。単独条件はその比較を含まない。
そこで**複合条件**（2つ以上の劣化を同時に掛ける）を検証基盤に追加した
（`generate.ts --mixed`）。真値が物理量ごとに定義できないので推定誤差の集計からは
外し、配点の検証だけに使う。

#### まず自分の条件設計の欠陥を踏んだ

最初は「ノイズ×残響」「ノイズ×音割れ」…と組を並べる形にした。結果、軸ごとの
相関が **音量 -0.52 / 音割れ -0.64** と符号が反転して出た。軸が壊れているように
見えたが、原因は条件の組み方だった——音割れの条件に強い残響が入っておらず、
残響の条件に音割れが入っていない。交絡である。

**完全要因配置に組み替えた**（SNR 3水準 × RT60 3水準 × 音割れ 2水準 ×
帯域制限 2水準 = 36通り）。要因が均衡していないと軸ごとの寄与は読めない。

#### DNSMOS が何に反応するかを先に測った

単独条件でのMOSの振れ幅（実音声4話者・16kHz）:

| 要因 | 範囲 | MOS | 振れ幅 |
|---|---|---|---:|
| SNR | 0 → 40 dB | 1.563 → 3.317 | 1.76 |
| RT60 | 0.2 → 1.5 秒 | 2.726 → 1.126 | 1.60 |
| クリップ率 | 0.0002 → 0.02（100倍） | 3.316 → 3.161 | **0.155** |

**音割れは100倍にしてもMOSがほとんど動かない。** モデルはノイズ抑制の出力で
学習されており、音割れの訓練信号をほぼ持たない。帯域は入力16kHzなので8kHz超が
見えない。**つまり音割れ軸と周波数軸の配点は、この方法では原理的に検証できない。**

これを知らずに相関を最大化する重みを探すと、必ず「音割れと周波数の配点を下げろ」
という答えが出る。モデルの盲点に合わせているだけで判定は良くならない。

#### 結果: オラクルが判断できる軸では現行配点が妥当

| 群 | 件数 | 現行配点のρ | 候補の範囲 |
|---|---:|---:|---|
| **ノイズと残響だけ**（モデルが判断できる要因のみ） | 36 | **0.800** | 0.775〜0.800 |
| 帯域制限なし（音割れを含む） | 72 | 0.209 | 0.056〜0.455 |
| 帯域制限あり | 72 | 0.327 | 0.218〜0.566 |

**判断できる要因だけに絞ると ρ=0.800 で、候補すべてが 0.775〜0.800 に並ぶ。**
現行配点に検出できる誤りは無く、同時にこの方法ではこれ以上の絞り込みもできない。

他の群の相関が低いのは配点の問題ではなく、モデルが音割れと帯域を見られないため。
実際、0.5%のクリッピングで自分の総合点は18点下がるのに、MOSは0.095**上がる**。

#### 残った較正できない部分

- **音割れ軸には使える外部基準が無い。** 実測すると 0.1% で 6.1/15点、
  0.5%以上は一律0点（0.5%と2%を区別できない飽和）。DNSMOSは 0.1% を
  ほぼ無害と見ている（3.316→3.282）。2つの基準が食い違い、決着できない。
  判定の行動（入力ゲインを下げる）は変わらないので飽和自体は許容し、閾値は動かさない。
- **残響軸の閾値も較正できない。** DNSMOSはRT60 0.5秒をSNR 3dB相当まで下げるが、
  検証基盤のインパルス応答は直接音対残響のエネルギー比を0.45に固定している。
  実際の部屋ではこの比はマイク距離と部屋容積で決まり、了解度に効くのはRT60より
  この比のほう。つまりモデルはRT60ではなく「合成が湿りすぎていること」に
  反応している可能性がある。この基盤ではRT60の閾値を較正できない。
  （RT60の**推定精度**の検証には影響しない。真値は構成上既知のまま。）

### 検証基盤側で見つけて直した2点

- **上げ変換に帯域制限を掛けていなかった。** 線形補間だけでは鏡像が残り、
  元素材に無い高域が乗って帯域上限の検出が狂う。両方向で帯域制限するようにした。
- **注入するノイズを全帯域で作っていた。** 暗騒音は音声と同じマイクを通るので、
  素材の帯域上限を超えてノイズだけが乗ることは現実には起きない。制限しないと、
  帯域制限された素材にノイズを足しただけで「広帯域の録音」に見えてしまい、
  加工痕跡の検出が意味をなさなくなる（実際に48kHzのSNR行が全部そうなっていた）。

### 残響の信頼判定を実測で締めた

減衰イベント数と誤差の関係（43条件）:

| イベント数 | 件数 | MAE | 最大誤差 |
|---|---:|---:|---:|
| >=3 | 37 | 0.069 | 0.361 |
| <3 | 6 | 0.168 | 0.370 |
| >=4 | 34 | 0.053 | 0.249 |
| <4 | 9 | 0.196 | 0.370 |
| >=5 | 33 | 0.053 | 0.249 |

4件を境に3.7倍の差が付き、5件に上げても利得が無い。信頼の閾値を3→4に上げた。
RT60 0.7秒以下では常に4件以上得られるので、判定に効く範囲を「参考値」に
落とす副作用はない（イベントが減るのは1.0秒以上で、その領域は残響軸がすでに最低点）。

効果: 確定値として出す行の MAE 0.069→0.053秒・最大 0.361→0.249秒。
誤差0.15秒超の行のうち参考値として開示できたものが 3/7 → **6/7**。

推定値のばらつき（イベントごとのRT60の四分位範囲÷中央値）でも同じ判別を試したが、
誤差と単調にならなかった（>0.7 のほうが <=0.7 より誤差が小さい）。件数のほうが素直。

### 話者を増やして初めて分かったこと

1話者では見えなかった問題が3つ出た。うち**2つは製品ではなく検証基盤側の欠陥**だった。

**(a) SNRが最大13.8dB外れていた（製品側の実問題）**

残響ガード（RT60ぶんのフレームをノイズフロア推定から除外する仕組み）が、
間の短い話者では無音をほぼ全部食い潰し、ノイズ用フレームが3〜4個に枯渇していた。
測れる量が確保できるまでガードを縮める安全弁を入れて最大誤差 13.8→4.1dB。

代替案として「無音のうち最も静かなN個を使う」も試したが、無音フレームの分布に
長い下裾があり選択バイアスで同じく+13dBの過大評価になった。実測で棄却した。

**(b) 帯域→周波数の相関が 0.827→0.535 に落ちた（検証基盤側の欠陥）**

素材をまとめて1つの相関にしていたため、話者間のスコア水準の差だけで順位が乱れていた。
素材ごとに求めて平均する方式に変えたら **1.0（完全に単調）**。製品側は正常だった。

**(c) 残響→ノイズの結合が「欠陥」と報告された（検証基盤側の欠陥）**

ρ=-0.414 だが、ノイズスコアの実際の変化は25点満点中 **2.25点**。順位相関は
スケールフリーなので、無視できるズレと本質的な欠陥を区別できていなかった。
これを「直そう」として、SNR精度を9dB犠牲にする方向へ動かしかけた。
効果量（軸スコアが実際に動いた幅）を併記し、満点の10%以上動いていなければ
結合とみなさないようにした。

### RT60の系統的な過大評価を補正した

4話者すべてで RT60 が過大評価（バイアス +0.09〜+0.27秒）だった。切り分けの結果:

- 合成したインパルス応答そのものを測ると**誤差±0.01秒で正確** → 推定器と
  インパルス応答合成に誤りはない
- 測定開始点を下げても悪化（+0.168→+0.249）、フロア余裕を変えても不変
- 推定値／真値の比が 1.20〜1.58（平均1.35）で**加算ではなく倍率として一定**

つまり「発話を通して観測した減衰は部屋のRT60より緩い」という実在の現象で、
無参照RT60推定に共通する既知の限界。発話は瞬時に止まらないので、観測できる減衰は
「部屋の応答 × 直前の発話エンベロープ」の畳み込みになり傾きが緩く出る。
倍率1.35で割り戻して バイアス +0.168 → **-0.036秒**、MAE 0.168 → **0.074秒**、
話者間のばらつきも -0.067〜+0.018 に収束した。

**この係数はこのコーパスで校正した値。** 発話速度や間の長さが大きく違う素材では
再確認が必要。単体テスト側は、純粋な指数減衰（発話の立ち下がりを持たない）に対しては
補正前の値で検証するようにした。

## 実測結果（実音声1話者・参考）

素材は **CMU ARCTIC**（16kHzモノラルのスタジオ録音、個別取得した40本を連結して3素材）。
90条件。詳細は `validation/report.md`。

| 推定対象 | 件数 | バイアス | MAE | 最大誤差 |
|---|---:|---:|---:|---:|
| 帯域上限[Hz] | 9 | 0 | 0 | 0 |
| クリップ率 | 12 | 0 | 0 | 0 |
| SNR[dB] | 48 | -0.32 | 1.34 | 4.07 |
| RT60[秒] | 15 | +0.031 | 0.094 | 0.264 |

単調性はすべて想定どおり（snr→noise +0.988 / clip→clip -0.922 /
cutoff→frequency +0.827 / rt60→reverb -0.922 / rt60→noise -0.162）。

MOSオラクルは実音声で**信用できる水準になった**（劣化なし素材のMOSが 2.33 → **3.496**）。
SNR ρ=0.977、残響 ρ=0.78。帯域はMOSの振れ幅が0.077しかなく読めない（自己診断が明示）。

### 実音声で初めて見つかった2つの欠陥

合成素材では検出できず、実音声で初めて出た。

1. **残響がノイズとして再び二重計上されていた**（rt60→noise が ρ=-0.446）。
   原因はノイズフロアの推定方法。`p05 + 3dB` では残響がフロアを持ち上げ、
   減衰の測定区間が途中で打ち切られて RT60 1.0秒以上がほとんど測定不能になり、
   RT60がnullだと残響の除外ガードが効かないためノイズとして数えられていた。
   `p02 + 2dB` に変えて RT60 1.0秒が3件すべて測定可能になり、結合は ρ=-0.162 に解消。
   RT60 の MAE も 0.123 → 0.094 秒に改善した。
2. **測定不能な残響が、実測した悪い部屋より高得点だった。** 測定不能時に満点の
   0.6倍(12/20)を返していたため、実測した0.7秒の部屋(13/20)と並び、
   「測れなかった部屋」が優遇されていた。0.5倍に下げ、さらに**測定できなかった軸が
   あるときは判定を good にしない**ようにした（測定不能な軸には中間点を与えている
   ので、そのまま断定すると測れなかった部屋が実測した悪い部屋より高評価になる）。
   判定文も「足を引っ張っている軸」とは別文にした——測定できなかった軸を
   低スコアの軸として提示すると誤解を招くため。

## 実測結果（合成音声風信号・参考）

検証基盤 (`npm run generate && npm run validate`) で実測した値。
素材は合成音声風信号3本（各10秒・製品のマイク録音と同じ長さ）、99条件。
詳細は `validation/report.md`。

### 推定誤差

| 推定対象 | 件数 | バイアス | MAE | 最大誤差 |
|---|---:|---:|---:|---:|
| 帯域上限[Hz] | 18 | 0 | 0 | 0 |
| クリップ率 | 12 | 0 | 0 | 0 |
| SNR[dB] | 48 | +0.24 | 0.67 | 2.45 |
| RT60[秒] | 16 | +0.006 | 0.076 | 0.319 |

着手前との比較:

| 推定対象 | 着手前 | 現在 |
|---|---|---|
| 帯域上限 | 検出不能（常にナイキストを返す） | 誤差0 |
| SNR | バイアス +2.81dB / MAE 3.14dB | +0.24dB / 0.67dB |
| RT60 | **推定器が存在しない** | MAE 0.076秒 |

### スコアの単調性（Spearman）

| 条件 | 軸 | 期待 | 着手前 | 現在 |
|---|---|---|---:|---:|
| SNR | noise | + | +0.997 | +0.991 |
| クリップ率 | clip | - | -0.927 | -0.927 |
| 帯域上限 | frequency | + | **0（無反応）** | **+0.941** |
| RT60 | reverb | - | 軸が存在しない | **-0.915** |
| RT60 | noise | 0（無相関であるべき） | **-0.889（二重減点）** | **+0.22** |

劣化なしのクリーン音声: 総合 **99/100**（着手前は81/100。音量が全体RMS由来で
11〜13/30しか出ていなかったため）。残りの1点は素材自身のノイズフロア(-55dBFS)による。

### 途中で判明した事実

- **周波数バランス軸は帯域という次元を見ていなかった。** カットオフ3.4kHz〜16kHzで
  スコアが一定（ρ=0）、しかも満点。当初「削るほど上がる」と表現したが実測ではそれ以上に
  悪く、電話品質もフルバンドも同点だった。分母を有効帯域内に限定するだけでは足りず、
  帯域幅を独立した内訳（8点）として加える必要があった。
- **残響がノイズとして二重に計上されていた。** RT60 0.2→1.5秒で noise が 20→12 に低下し、
  同時に volume が 15→21 に上昇（残響が全体RMSを理想帯域に押し上げる）。2つの誤りが
  相殺して総合点がほぼ動かず、正常に見えていた。SNR推定に推定RT60を渡し、
  残響が減衰しきるまでのフレームをノイズフロアの推定から除外して解消した。
- **帯域上限の検出は解析窓のリーク床で律速されていた。** ハミング窓(-43dB)ではリーク床が
  約-70dBに居座り、コーデックが削った領域と窓自身のリークを区別できなかった。
  Blackman-Harris窓(-92dB)に変えて崖が-51dB→-103dBになり検出可能になった。
- **SNRの有音/無音分離は固定閾値では成立しなかった。** ピークから25dB下の固定閾値では
  SNRが25dBを下回ると無音フレームを1つも分離できず、発話パワーを全フレーム平均で
  代用していた。その結果、無音の割合ぶん(実測 -3.0dB)過小評価していた。
  フレームレベルの1次元2-meansに変更し、ノイズの定常性（下側の群の標準偏差）で
  二峰性を判定するようにした。
- **「注入した量」を真値にしてはいけなかった。** 素材自身のノイズフロアがあるため、
  40dB下にノイズを注入しても実際のSNRは36.2dBで飽和する。これを無視していたため
  推定器が正しいのに -3.81dB の誤差が出ているように見えた。真値の定義を直したら
  その条件の誤差は -0.02dB になった。実音声コーパスでも同じ問題が起きる。
- **残響の推定は「遅い側が部屋」ではなかった。** 減衰率分布の上側パーセンタイル(p75)を
  採る設計を試したが、実測では中央値が明確に正確だった（真値0.2〜1.0秒に対し
  p50の誤差0.02〜0.11秒、p75は0.02〜0.27秒）。残響が掛かった時点で発話自体の減衰も
  残響に律速されるため、分布全体が部屋を反映する。

## 実装した内容

### 手順1: 測定経路の修復

- `getUserMedia` の `echoCancellation` / `noiseSuppression` / `autoGainControl` を明示的に false
- **生PCMの直接取得**（AudioWorklet）。`MediaRecorder` の Opus は再生用のみに使う。
  Opusのノイズシェーピングが測定対象そのもの（無音区間のノイズフロア）を書き換え、
  DTXが無音を完全な0にしうるため自作の検出器が自分の録音を誤検出する
- `provenance.ts` — 帯域上限の実測・デジタル無音・完全無音の連続を検出
- `signal.ts` / `estimators.ts` — DOM非依存に分離。Node側の検証から同じコードを呼ぶため
- 警告パネルを総合点の**上**に配置し、影響を受ける軸に「参考値」バッジ

### 手順2〜4: 評価軸の再構成

| 軸 | 配点 | 変更内容 |
|---|---:|---|
| ノイズ | 25 | 無音区間の割合評価(6点)を削除。SNR推定を2-means分離＋混合パワー補正＋残響除外に |
| 周波数バランス | 25 | 分母を有効帯域内に限定。帯域幅(8点)を新規追加 |
| 残響 | 20 | **新規**。発話オフセットの減衰率分布からRT60を推定 |
| 音量 | 15 | 全体RMS→有効音声レベル(ITU-T P.56相当)。ダイナミクス評価(8点)を削除 |
| 音割れ | 15 | 配点のみ変更 |

### 手順5: 検証基盤

`npm run generate` / `npm run validate` / `npm run fetch-corpus`。
公開コーパスはgit管理外、記録（manifest / report）のみgit管理下。

### 手順6: 出力の再設計

- 判定パネル（結論＋足を引っ張っている軸）。**総合点の平均ではなく最も低い軸**で決める
- 実測値の表示（SNR / 残響時間 / 帯域上限 / 発話レベル / クリップ率）
- 録音前に読み上げ文の例と緩い指示を提示

### 追加: アドバイス文の i18n 化

アドバイスは分析側で日本語を組み立てていたため、EN モードでもアドバイスだけ
日本語で表示されていた（着手前から存在していた不具合）。
`AudioScores.advice` を文面から `{ code, value? }` に変え、文面は i18n 側へ移した。
テストの文字列照合（`advice.some(a => a.includes('音割れ'))`）もコード照合に置き換え、
全コードの両言語網羅と「英語側に日本語が混ざっていないこと」を検証するテストを追加した。

### 追加: 実音声コーパスの経路整備

既定の取得元を **CMU ARCTIC（WAV配布・約115MB）** に変更した。FLAC 配布の
LibriSpeech だけを候補にしていたため ffmpeg が必須になっており、実音声検証に
着手できない状態だった。CMU ARCTIC は WAV なので ffmpeg 不要。

あわせて2点を直した。

- **コーパスファイルの連結。** 公開コーパスの1ファイルは2〜4秒の単発発話が普通で、
  そのままでは残響の自由減衰を観測できる息継ぎが足りない。目標長(10秒)に達するまで
  連結するようにした。目標長の80%に届かない余り物は素材にしない。
- **`has()` のバージョン確認フラグ。** `-version` 固定だったため curl / tar を
  「存在しない」と誤判定していた（ffmpeg は `-version`、curl や tar は `--version`）。

この経路は、公開コーパスと同じ形式（16kHz・2〜4秒の単発WAV）のファイルを
一時的に置いて実際に通した。連結・レベル揃え・短い余りの除外まで動作を確認済み。
16kHz素材での実測は RT60 MAE 0.040秒、帯域上限 ρ=1.0 だった。

**ただし本物の公開コーパスのダウンロードは実施していない**（115MBの取得を中止したため）。
実音声での検証は未了のまま。`npm run fetch-corpus` を実行すれば着手できる状態にはある。

### 追加: MOSオラクル（DNSMOS）を実際に動かした

モデル取得を `npm run fetch-mos-model` としてスクリプト化し、`onnxruntime-node` を
devDependency に入れて `npm run validate -- --mos` を通した。
入出力の仕様は DNS-Challenge の `dnsmos_local.py` に合わせた
（16kHzモノラル / 9.01秒=144160サンプル / 入力名 `input_1` / 形状 `[1,N]` /
出力 `[SIG,BAK,OVRL]` の生値に多項式補正）。
当初書いたコードは9.00秒・ホップ未実装・多項式補正なしだったので直した。

**結果は「オラクル自体は動くが、合成素材では信用できない」**。

| 条件 | ρ | 判断 |
|---|---:|---|
| rt60 | **+0.948** | 一致。MOSが 2.78→1.08 と大きく動いており信号として強い |
| snr | **+0.855** | 一致 |
| cutoff | **-0.776** | **信用できない**（下記） |
| clip | -0.251 | MOSの振れ幅0.30と小さく読めない |

帯域制限の不一致を採用してはいけない理由が2つ、実測で判明した。

1. **DNSMOSの入力は16kHzモノラルなので8kHz超のカットオフが原理的に見えない。**
   `lp8000` / `lp11000` / `lp16000` の MOS が完全に同一値（clean と同じ）だった。
   6条件のうち3つが情報ゼロ。
2. **劣化なしの合成音声のMOSが 2.33 / 5 しかない。** 素材がモデルの学習分布から
   外れており、モデルは帯域ではなく合成の不自然さ（インパルス列由来の高域の
   ざらつき）を評価している。ローパスでそれが削れるので「狭いほど良い」と出る。

つまり周波数バランス軸をこの信号で「修正」してはいけない。
この判断を人手に頼らないよう、**レポート側に自己診断を組み込んだ**:
劣化なし素材のMOSが3.0未満なら警告を出し、条件ごとに「異なるMOS値の個数」と
「MOSの振れ幅」を並べて、情報が無い相関を見分けられるようにした。

コスト: `onnxruntime-node` は約259MB。依存の `adm-zip` に high severity の勧告があるが、
onnxruntime-node のインストールスクリプト経由でのみ使われ製品バンドルには入らない。
`npm uninstall onnxruntime-node` で外しても検証の主軸は動く。

## Open questions
- 周波数軸の内訳を「有効帯域幅15点 + 1kHz以上の傾斜10点」にしたが、傾斜の採点境界
  （-10dB/octで満点 / -22dB/octで0点 / 0dB/octを超えたら減点）は**4話者から置いた値**。
  自然な傾斜が -2.4〜-8.8dB/oct と6.4dB/octも幅があり、声の暗い話者が減点されない
  ことを保証できるだけの素材数がない。素材を増やしたら必ず見直す。
- 「低域が過剰（こもり）」「高域が過剰（キンキン）」の検出は捨てた。前者は声質を
  測っていたため、後者は実音声で一度も発火せず検証条件も無かったため。マイクの
  近接効果のような「低域だけが過剰」な欠陥は現在どの軸も捉えていない。
- 劣化なしのスタジオ録音が総合100点で並ぶ（4話者すべて）。目的が適否の判断なので
  上限で飽和するのは正しいが、良い録音同士の差は付かない。
- 配点（ノイズ25 / 周波数25 / 残響20 / 音量15 / 音割れ15）は、DNSMOSが判断できる
  要因（ノイズ・残響）については検証済み（複合条件36件で ρ=0.800、候補すべて
  0.775〜0.800で並ぶ）。**周波数軸と音割れ軸の配点は原理的に検証できない**
  （モデルは8kHz超の帯域差を見られず、クリップ率100倍でMOSが0.155しか動かない）。
  別の根拠が必要。判定閾値（達成率75%/50%）も未検証。
- 残響軸の閾値（0.4秒で満点 / 1.2秒で0点）は較正できていない。検証基盤の
  インパルス応答が直接音対残響比を0.45に固定しているため。実際の部屋ではこの比が
  マイク距離と部屋容積で決まり、了解度にはRT60よりこの比のほうが効く。
  比を要因として振れるようにするのが次の一手。
- 処理済み音声の判定閾値は実録音2本で確認した（PCのノイズ抑制ゲートを
  digital-silence + zero-run で検出、ゲート無しのスマホ録音は痕跡なしと正しく判定）。
  ただし2本だけで、Zoom/Teams 経由の音声そのものは未検証。
- 崖の落差の閾値25dBは高ビットレートAACに対して際どい（実録音で22.5dBを取り逃がした）。
  判定への影響は無いが、より高い帯域のカットオフを測りたい場合は要検討。
- 実録音は3本、話者1名。**うち2本（PC録音）は形式が可逆WAVでも中身が8kHz帯域**で、
  Windowsの音声処理パイプラインを通っている。8kHz以上に本物の中身がある実素材は
  スマホ録音（16kHz帯域）1本だけ。11kHz以上の帯域を持つ実素材は未取得。
- 崖の落差の閾値25dBは据え置いた。窓幅を複数にしたことで実録音の崖（1000Hz遷移）が
  29.9〜35.0dBで通るようになったため。ただし余裕は5〜10dBしかない。
- **このツール自身のマイク録音でもOS/ドライバのゲートがかかるかは未確認。** かかる場合、
  ブラウザからは切れないので案内するしかない（案内は入れた）。実機で確かめたい。
- SNR 0dB付近では有音/無音が分離できず代替手段（p20）に落ちる。実測の誤差は
  -0.46dB（安全側）まで下げたが、分布が重なるため原理的に精度は出ない。
  判定閾値(SNR 15dB)から遠いので優先度は低い。
- **録音に背景雑音だけの区間が1つも無い場合、SNRは原理的に測れない。**
  しかもその状態を信号から検出できない（無音フレームの連続長で判別しようとしたが、
  実音声の語間も2〜3フレームしかなく完全に重なった）。最悪ケースではSNRを
  25〜48dB低く読む＝静かな部屋を騒がしいと言う。実素材では観測されておらず
  （人為的にフレームを削って作った条件）、対策は入れていない。
  スペクトルの定常性で判別する手はあるが、実害が確認できていない対策に
  フレームごとのFFTを追加する判断は保留。
- SNR 5〜20dB に分子の +1.2〜+2.5dB の偏りが残る（2群分離の境界が発話分布の
  内側に来るため）。分母の同方向の偏りとほぼ打ち消し合うので合計誤差は小さい。
  低SNRでは無音と小さい声が原理的に区別できないため、これ以上追うと過適合。
- MOSオラクルは実音声で信用できる水準（劣化なし素材3.496）。ただし**合成素材では
  信用できない**（同2.33）ので、素材を変えたら必ずレポートの自己診断を確認すること。
- DNSMOS の入力は16kHzなので、8kHz超の帯域差は永久に見えない。帯域幅の配点を
  MOS相関で検証することは原理的にできない。別の根拠（規格・実聴取）が必要。
- 素材は CMU ARCTIC のみ（4話者）。すべてスタジオ録音で、素材自身のSNRは26.5〜30dB。
  実際の会議室・スマホ録音のような素材での検証は未実施。
- **8kHz以上に本物の中身がある素材での検証が未実施。** 48kHzでの実装の正しさは
  確認したが（16kHz素材を上げ変換して両レートで一致）、上げ変換では8kHz以上に
  中身は生まれないので、8/11/16kHzのカットオフ条件は試せていない。
  48kHz収録の公開コーパス（VCTK など）が必要だが、いずれも単一の巨大アーカイブ
  配布で、個別ファイル取得ができない。
- RT60の補正係数(1.35)は**削除した**。非現実的に湿った素材(DRR -17dB)で校正した値で、
  現実的なDRRでは逆方向に働いていた。
- 残響が測れる範囲は DRR +5〜+15dB（MAE 0.10〜0.18秒）。その外では ±0.18〜0.24秒の
  バイアスが出る。DRRを無参照で推定して補正する手はあるが難問で、素材依存の係数を
  入れる誤りを一度やっているのでやらない。
- 実際の録音のDRRがどう分布するかは実素材3本しか見ていない。
- 複合条件の表がSNR側とRT60側で知覚的な振れ幅が揃っていない。配点の候補間に差が
  出るようになったが（現行0.859 / ノイズ寄せ0.929）、その差は条件の選び方を
  反映している可能性がある。知覚的に釣り合った条件表が必要だが、オラクルで作って
  オラクルで検証すると循環する。別の根拠が要る。
- RT60 1.5秒以上は3件中1件しか測定できない。会議室の実用域(0.4〜0.8秒)は
  網羅できているが、極端に反響する空間では測定不能になる。
