# 設計: ハウリングチェック

ルート: `/howling`　状態: **実装済み**
前提: [受動リアルタイムモニターの骨格](./realtime-monitor.md)

## この機能が答える問い

**「いま鳴いているのは、どの周波数か。」**

鳴っていること自体は部屋の全員が気づいている。画面を見る必要はない。しかし
**3.2kHz なのか 4.5kHz なのかは、人間の耳では区別できない。** どのフェーダーを、
どのEQバンドを下げればよいのかが分からない。そこを数値にするのがこの道具の全てである。

## 誰が、いつ開くか

**PAを触る本人が、自分のスマホで見る。** EQ（グライコまたはパラメトリックEQ）を
触れる人に限定している。触れない人にとって「3.2kHz」は行動に変換できず、打てる手は
ゲインを下げる・マイクを動かすくらいで、周波数は関係ない。その人向けに作ると
この道具は「対処法を教えるアプリ」になり、**測定である必要が無くなる**。

**使い方は「ハウった後に開いて、次に鳴くのを捕まえる」。** イベント中ずっと
動かし続ける前提は取らない。したがってセッションは数分で、**その99%は
「待っている時間」**である。待っている画面こそがこの道具の画面になる。

## やらないこと（意図的に）

- **なきかけ（precursor）の判定はしない。** ループゲインが1に近づいた段階での予兆判定は、
  空調・電源ハム・プロジェクタのファン・歌声の持続音と区別がつかない。空調を指して
  「危険」と言い出したツールは二度と信用されない。**鳴ってから指させばよい。**
  ただし**突出度そのものはバーで見せる**——禁じるべきは断定であって、測定値の提示ではない。
- **音を出さない。** 端末の内蔵スピーカーは会議室のPAではないので、能動プローブで
  測れるのは端末自身のマイク–スピーカー間ループだけであり、現場の問題を説明しない。
  さらにAECを切ったまま自分で音を出すと、**ツール自体が本物のハウリングを起こしうる。**
- **止めたら何も残さない。** 履歴もサマリも保存も作らない。
- **点数を出さない。** 刻々変わるものに点数は付かない。
- **長時間運用に配慮しない。** 90分動かしっぱなしにする前提を取らないので、
  発熱・電池の配慮と Wake Lock の保証は扱わない（Wake Lock は best-effort で
  取るだけで、取れなくても失敗にしない）。

## 出力

**オクターブバンド名を主、周波数を併記。**

```
   発振中
   4k帯 ／ 3.20 kHz
```

固定バンドのグライコしか無い現場では「4k帯」がそのまま操作になる。
パラメトリックEQがあるなら数値が効く。両方出すコストはほぼゼロ。

状態は**2段**しかない:

| 状態 | 意味 |
|---|---|
| 聞いています | 突出した狭帯域ピークが持続していない |
| 発振中 | 突出が持続している。周波数を表示する |

設計当初あった「注意」（突出はあるが持続していない）は**作らなかった**。咳・拍手・
椅子を引く音で光り、周波数も出さないので行動に変換できない。待っている数分間に
何度も光れば、オペレーターは画面を見るのをやめる。「注意」の唯一の実用的な役目
（この道具が生きていることの提示）は、100msごとに動くバーのほうがうまく果たす。

### 履歴（直近3件）

鳴き終わった周波数は、**次の発振が確定するまで画面に残る**。時間で消さない——
鳴いた後にケーブルを挿し直したり人と話したりで平気で30秒経つので、10秒で消すと
**画面を開いた理由そのものが消える**。古い数字の誤読は経過秒（「3分20秒前」）の
併記で防ぐ。

同じ周波数（±3%）は1行にまとめ、回数と合計秒で持つ。まとめないと、繰り返し
鳴いているという**利用者がこの道具を開いた理由そのもの**が、同じ行の重複で
画面を埋めてしまう。

1件ではなく3件持つのは、`3.2kHz → 3.2kHz → 5kHz` という**並びそのものが診断**だから
である（3.2kHzを切ったせいで次のピークが出た、と読める）。

## 検出

100ms ごとに直近 `FFT_SIZE = 4096` サンプルのスペクトルを取り、3つを見る。

**1. 突出（狭帯域性）**
ピークが、その周辺の中央値に対して何dB持ち上がっているか。閾値 21dB。
ハウリングは1本の細いピークとして立つ。広帯域のノイズでは立たない。

中央値は**ピークの上下両側から取り、大きいほうを床にする**。片側だけで取ると、
スペクトルの傾き（低域ほど大きい）が突出度に化ける。片側のビンが足りない周波数では
**0を返す＝測れないと言う**——突出していないのではない。

**2. 持続**
同じ突出が **3フレーム** 連続しているか。「同じ」は**±1ビン かつ ±2%**である。
拍手・咳・机を叩く音は突出するが持続しない。

設計時は500msだったが、腕のいいオペレーターはハウリングを 0.2〜0.5秒で殺す。
500msを要求すると**その人の現場では一つも捕まらない**。拍手はインパルス（10〜20ms）
なので桁が2つ違い、3フレームでも弾ける。

窓(85ms)がホップ(100ms)より短く重なりが無いので、3フレームが要求する連続長は
250msではなく**実測で約300ms**である（0.15秒 0% / 0.2秒 20% / 0.25秒 70% /
0.3秒 100%、初検出までの遅れは中央値290ms）。0.2〜0.5秒のうち**下半分は捕まらない**。
ここを詰めるにはホップを縮めて窓を重ねるしかなく、計算量と引き換えになる。

**「同じ」に比を併せるのは、ビンだけでは低域で緩すぎるからである。** ビン幅 11.7Hz は
3.2kHz に対して ±0.37% だが 210Hz に対しては ±5.6%（約95セント）で、同じ規則が
下端では約15倍緩い。半音近く動いても「同じビン」になるので、**声の基音の揺れが
そのまま持続と読まれる**。実音声で出た空振りはすべてこれだった（下記）。
発振の周波数はループの位相条件で決まって動かないので、比で締めても本物は落ちない。

**3. 倍音列でないこと**
本番中（BGMや喋りが流れている最中）も対象に含めたので、この判定は省けない。
伸ばした歌声・シンセのパッド・楽器の音は、細いピークとして数秒持続するため、
「突出＋持続」の2条件だけでは**ハウリングと区別がつかない**。

2方向から見る。`f/2 〜 f/5` に有意なピークがあれば `f` は上の倍音。`2f` と `3f` の
両方にあれば `f` は倍音列の基音。どちらも**注目しているピークと同程度の強さ**
（−12dB 以内）を要求する——声の倍音列は基音おきに立つので、絶対値の下限だけだと
**どんな周波数の 1/2 の近くにもたまたま何かが居て**、本物の発振が落とされる。

3つすべてを満たしたときだけ「発振中」にする。

周波数はピークとその両隣3点をdBで放物線補間して求める。11.7Hz のビン幅より細かい値が出る。
補間はピークをビン中心から最大±0.5ビン動かすので、**求めた周波数は走査したバンドの
中へ収める**。収めないと、バンドの縁で「発振中なのにバンド名が無い」が起きる
（48kHz・FFT4096 では最上位ビンが 11308.6Hz、+0.5ビンで 8kHz帯の上端 11313.7Hz を
超える）。そうなると画面は赤くなるのに文字は「聞いています」のままになり、
履歴にも残らない。**表示する周波数は、表示するバンドの中にある**——この不変条件を
構造的に保証している。

### FFT長とバンド

FFT は音質チェックの 2048 ではなく **4096**（48kHz でビン幅 11.7Hz・窓長 85ms）。
2048 では 63Hz がビン2.7本目・125Hz が5本目で、突出判定に使える下側のビンが無い。

表示バンドは ISO のオクターブ中心周波数で **250 / 500 / 1k / 2k / 4k / 8k**（Hz）。
**63Hz帯と125Hz帯は載せない。** 4096 でも 125Hz はビン10.7本目で、ガード幅(±6)を
引くと下側に使えるビンが1本も残らない。実測でも、125Hz帯を載せていたときに
**基音110Hzの歌声を「110Hzで発振中」と誤検出した**。250Hz帯は 176.8Hz から始まるので、
演台マイクの 200〜500Hz の鳴きは引き続き測れる。

**測れない箱だけを並べない**——それが 63Hz帯と125Hz帯を外した理由である。

なお **250Hz帯と500Hz帯は、載っているが感度が低い**。実音声の上に注入した鳴きで、
1.25kHz以上なら振幅0.03で全件捕まるのに対し、200Hz・320Hz は0.03で0%、0.12で100%
だった。**下端の2バンドは他より約6dB大きい鳴きを要求する。** 声のエネルギーが
周辺の中央値（突出度の分母）を持ち上げるためで、これは物理の側の話である。
演台マイクの 200〜500Hz の鳴きは測れるが、**小さいうちは捕まらない**。

## 閾値をどちら側に倒すか

**空振り（誤検出）は見落としより重い。** プロジェクト全体の原則と結論は同じだが、
**理由が違う**。音質チェックでは「無駄な作業をさせるから」だが、ここでは
**利用者に検算の手段が無いから**である。

利用者は耳でハウリングを聞いているので、見落としには気づける（鳴いたのに画面が
動かなかった、と分かる）。空振りには気づけない——鳴っていないのに出た数字を、
さっきの鳴きの正体だと信じてしまう。**気づける失敗より、気づけない失敗が重い。**

閾値（突出度 21dB）は合成信号で決めた。ノイズだけを12通りの乱数系列で流すと
単一フレームの突出度は最大 16.5dB まで上がるので、18dB では余裕が 1.5dB しかない。

## 測れていないときに黙らない

この道具には「静かに間違える」経路が1つだけある。**入力の飽和**である。

ハウリングが大きく鳴っているとき、スマホのマイクはそれ自体が飽和する
（`autoGainControl: false` で切れるのはソフトのAGCだけで、ハード側のリミッタは切れない）。
飽和すると広帯域の歪みが乗って**周辺の中央値が持ち上がり、突出度の分母が上がる**。
つまり**鳴きが大きいほど検出しにくくなる**。利用者からは「一番はっきり鳴いたのに
画面が動かなかった」＝「壊れている」に見える。

そこで飽和を検出したら申告する（「端末を音源から離してください」）。
飽和の検出だけはホップの隙間も含めて**全サンプル**を見ている。

同じ理由で、**チャンクが 1.5秒 届かなかったら計測を止め、「計測が止まりました」と
再開ボタンを出す**。「何も鳴っていない」と「何も測っていない」が同じ見た目に
なるのを防ぐ。開いたまま警告するのではなくマイクを閉じるのは、再開したときに
必ず作り直した検出器で測り直すためである。

**止まる直前に捕まえていた周波数は残す。** 「止めたら何も残さない」のは
*利用者が止めたとき*の話であり、画面が消えて勝手に止まったときまで消すと、
この道具を開いた理由そのものが消える。ただし**経過秒は捨てる**——止まってから
何分経ったか分からないのに「12秒前」と出すのが、この道具で最も避けたい誤読だから。

止めるときは**鳴っている最中の発振も確定させてから**残す（`finish()`）。
画面が消えるのは鳴っている最中かもしれず、そこで落とすと一番肝心な1件が消える。

なお 48kHz では窓(85ms) < ホップ(100ms) なので、**フレーム間に約15msの見ていない
隙間がある**。持続する発振には影響しないが、そこは正直に書いておく。

## 状態機械

```
idle ──(開始)──> listening ──(停止)──────> idle
                    └──(計測が途切れた)──> stalled ──(再開)──> listening
                                             └──(停止)──> idle
```
マイク拒否・失敗は `error` に入り、「もう一度試す」で `idle` に戻る。

`done` は無い。`analyzing` も無い（聞きながら解析している）。
この状態機械は `src/lib/audio/session.svelte.ts` にあり、ボリュームチェックと共有する。

## 画面

```
[ 状態（大きく） ]
[ バンド名 ／ 周波数 ]        ← 発振中のみ
[ 飽和・計測停止の警告 ]      ← 出るときだけ
[ 突出度のバー6本＋閾値の線 ]
[ 直前に鳴いた周波数（最大3行・経過秒つき） ]
[ 使用中のマイク名 ]
[ 停止 ]
```

バーは**レベル(RTA)ではなく突出度**。素直なオクターブバンドのレベルだと、会議室で
最も高いバーは常に250〜500Hz（人の声）になり、**検出しているものがバーに現れない**。
突出度なら表示と判定が同じ量になり、閾値に近づいていくのが見える。

マイク許可の前は、何をする機能かの説明と開始ボタンだけを出す。

## 検証

真値を注入した信号で測る（`src/features/howling/detector.test.ts`、
信号の生成は `src/test-support/signals.ts`）。
人手のラベル付けは不要——注入した周波数がそのまま真値になるからである。
`validation/` には置かない。復号も要らず、判定がその場で出せるので、
ユニットテストの中で適合率と再現率が出せる。

**合成信号: 適合率 1.0 / 再現率 1.0**（陽性7件・陰性12件）。加えて閾値の余裕も測る。

陽性: 200 / 320 / 1050 / 3200 / 7500Hz の発振、0.4秒で殺された短い鳴き、
喋っている最中の発振。

陰性: 無音、ピンク／白色ノイズ、空調のような定常ノイズ、電源ハム 50Hz・60Hz と
その倍音列、拍手、伸ばした歌声（ビブラート有無）、BGMのパッド（3和音）、
0.15秒しか鳴かなかった音、プロジェクタのファン（広帯域の緩い山）。

余裕の検証: ノイズを12通りの乱数系列で流して一度も指さないこと、
基音を9通り変えた歌声をどれも発振と呼ばないこと、ノイズだけのときの突出度が
閾値に対して 3dB 以上の余裕を持つこと。

### 合成信号だけでは足りない

**合成した倍音列は倍音の強さが規則正しすぎて、倍音判定にとって都合が良すぎる。**
本物の声は母音・声道・声門の都合で倍音の強さがフレームごとに大きく揺れ、そこで
「2f と 3f の両方」の AND が外れる。上の陰性12件を全部通した状態で、
実音声（CMU Arctic 65本・レベル9条件・計585試行＝発話約39分）を流すと
**26件(4.4%) の空振り**が出た。**全件が 189〜314Hz（250Hz帯）で、うち24件が
女性話者**である。持続判定に ±2% を併せて 2件(0.3%) になった。

そこで `fixtures/corpus/` があるときだけ効く実音声の陰性ケースを置いている
（`src/test-support/corpus.ts`）。**素材は git 管理外なので CI では黙って飛ぶ。**
手元で `npm run fetch-corpus` を通した人にだけ効く柵である。陰性だけ足すと
「常に黙る」実装が通ってしまうので、同じ素材に発振を注入した陽性も対にしている。

これは文献側の指摘とも一致する——合成トーンは狭帯域・定常のフィードバックしか
表現せず、実世界の時変トーナルドリフト・多倍音構造・非線形歪みを反映しない
（Mounir et al., EURASIP JASMP 2025）。

### 文献との対応

この検出器の3つの判定は、ハウリング検出の標準的な特徴量と対応している
（van Waterschoot & Moonen, JAES 58(11), 2010 / Mounir et al., EURASIP JASMP 2025）。

| ここでの呼び方 | 文献での名前 | 違い |
|---|---|---|
| 突出（狭帯域性） | PNPR | 文献は近傍数ビンの固定オフセット。ここは幅を中心周波数に比例させた**中央値**を上下から取る |
| 倍音列でないこと | PHPR | 文献は m∈{2,3,4}。ここは f/2〜f/5 と 2f∧3f |
| 持続 | IPMP | 文献は過去 QM フレーム中の出現数。ここは連続数 |
| （作らない） | IMSD | 立ち上がりの傾きで予兆を見る特徴量。文献の実測で全特徴量中**最下位**（音声 F1=0.13 / 音楽 F1=0.05、閾値に極端に敏感）。**なきかけを判定しないという判断は、実験的にも支持される** |
