# 設計: 受動リアルタイムモニターの骨格

対象: ハウリングチェック / ボリュームチェック
状態: **両方とも実装済み。共通化は済んでいる。**

## どこまで共通化してあるか

抽象は利用者が現れてから切り出す、という順番で進めた。利用者が一人もいない層は
正しさを検証できず、次の機能を書き始めた瞬間に「合っていない」と分かるためである。

`src/lib/` は目的で分けてある:

- `audio/` — 音の出入り。`capture.ts` の `startMonitor`、
  `session.svelte.ts` の `MonitorSession`（開始・停止・失敗の分類だけを持ち、
  解析は一切知らない）、`wav.ts`
- `dsp/` — 信号処理。統計・FFT・スペクトル・ピーク・biquad・聴感補正・
  オクターブバンド
- `stream/` — 終わりの無い流れの骨組み。フレーム化・移動窓・環状バッファ

判定（何を発振と呼ぶか、何dBで音割れとするか）と画面は各機能の中にある。

## 音質チェックと同じ形にしてはいけない理由

| | 音質チェック | ハウリング / ボリューム |
|---|---|---|
| 取り込み | 10秒で自動的に終わる | 終わりが無い。止めるまで聞き続ける |
| 状態 | `idle → recording → analyzing → done` | `idle → listening`（`done` が無い） |
| 出力 | 100点満点の採点と静的な結果画面 | 刻々変わる状態表示。点数という概念が無い |
| 終了時 | 結果が残る（保存・再生できる） | 何も残さない（履歴もサマリも作らない） |

同じ状態機械に乗せると両方が歪む。`AppState` を共有しないこと。

## 共通化するもの / しないもの

**する**

1. マイクの獲得と `AudioContext` のライフサイクル（`src/lib/audio/capture.ts`）
2. マイクの状態機械（`src/lib/audio/session.svelte.ts`）——受動リアルタイムの2機能だけ
3. 信号処理プリミティブ（`src/lib/dsp/`）
4. 流れのフレーム化と移動窓（`src/lib/stream/frames.ts`）——入れ物だけ
5. シェル（ヘッダー・ルーティング・言語・`src/shell/app.css` のパネル）
6. 監視画面の外殻——開始前パネル・読み取り画面・停止パネルの見た目
   （`src/shell/app.css` の `.btn-primary` `.note` `.error` `.readout` `.hint` `.device`）
7. 状態機械の状態の呼び名（`src/features/common-text.ts`）——停止・もう一度試す・
   計測が止まりました・使用中のマイク・マイク拒否の6語。**値が同じものだけ**を配る。
   再開ボタンが "Resume listening" と "Resume measuring" に割れるのは測っているものが
   違うからで、揃えるべき差ではない

**しない**

- 解析パイプライン（`analyzeSamples` の「バッファをもらってスコアを返す」形）
- 音質チェックの状態機械（`idle → recording → analyzing → done`）。
  受動リアルタイムの `idle → listening` と同じ入れ物に乗せない
- フレーム化と移動窓の集計（下記「予告のうち…」を参照。形が違う）
- `VuMeter` / `RadarChart` / `ScoreBreakdown` / `VerdictPanel`（すべて音質チェック専用）

## 実装済み: `audio/capture.ts` のストリーミング取得

既存のワークレット（生PCMを main thread へ流す仕掛け）はそのまま使えた。
`setupRawCapture()` が `parts[]` に溜めていた部分を外し、都度コールバックへ渡すだけで
ストリーミングになる。配線は `attachPcmWorklet()` に切り出して両者で共有している。

```ts
export interface Monitor {
  /** マイクを閉じ、AudioContext を破棄する。二度呼んでも安全 */
  stop: () => void;
  /** 解析側が周波数を扱うために必要 */
  sampleRate: number;
  /** 実際に開いたマイクの名前 */
  deviceLabel: string;
}

export function startMonitor(
  onChunk: (samples: Float32Array) => void,
): Promise<Monitor>;
```

`recordMicrophone()` はこの上に実装し直せる（一定時間ぶん溜めて止める）が、**移行は
必須ではない**。音質チェックは動いており、動いているものを触る理由が無い。

実装して分かったこと：

- `AudioContext` は自動再生ポリシーで `suspended` から始まることがある。
  動かないと `process()` が呼ばれないので、`resume()` してから配線する。
- `stream.getAudioTracks()[0].label` で開いたデバイス名が取れる。
  `enumerateDevices()` を呼ぶ必要はない。
- A特性のようなサンプルレート依存の係数を持つ解析は、`AudioContext` のレートが
  確定してからでないと初期化できない。**最初の数msぶんのチャンクは捨てる**設計にした。

## 取り込み時の制約（全機能で共通・変更禁止）

```ts
{ echoCancellation: false, noiseSuppression: false, autoGainControl: false }
```

音質チェックではノイズフロアと音量を測るために必要だった。ハウリングでは
**より強い理由がある**——エコーキャンセラは、まさに検出したい発振をブラウザが
先に消してしまう。この3つがONの状態でハウリングチェックは成立しない。

## 予告のうち、当たったものと外れたもの

このドキュメントは以前「フレーム化・移動窓・状態機械の3つをハウリングを書くときに
切り出す」と予告していた。両方の実装を書いて読み比べた結果は次のとおり。

**半分当たった: フレーム化。** 切り出せたのは**区切り方**だけである
（`stream/frames.ts` の `FrameSplitter`）。**何を積むかは共通化していない**——
ボリュームは波形を捨てて二乗和だけ持てばよく、ハウリングはFFTのために波形そのものを
4096点保持する必要がある（`SampleRing`）。そこまで一つにすると、ボリュームに
要らない波形を持たせることになる。

**半分当たった: 移動窓。** 「直近N件だけ保つ」入れ物（`RingWindow`）は共通で、
**何を積んで何を取り出すかは各機能**——ボリュームはパワーの平均と瞬時値の最大、
ハウリングは飽和フレームの有無。

**当たった: 状態機械。** `idle / starting / listening / error` は完全に同じだった。
`audio/session.svelte.ts` に切り出し、**ボリュームチェックも新しい実装に載せ替えた**
（片方だけ載せ替えると「同じものが2つ」になり、次に直すときどちらを直したか
分からなくなる。`recordMicrophone` を残した判断とは状況が違う——あちらは
バッチとストリーミングという*別物*が並んでいるだけである）。

切り出した理由は行数ではなく、**間違えても気づきにくい**からである。
二重に開始ボタンを押されるとマイクが2本開く、許可ダイアログが出ている間に画面を
離れられるとマイクが開きっぱなしになる、古い起動から届くチャンクが新しい解析器に
混ざる——どれも動かして気づけない種類の壊れ方で、書き写すと写し間違いにも気づけない。

`MonitorSession` は2つの任意機能を持つ。**両機能が使う**:

- `stallMs` — この時間チャンクが届かなかったらマイクを閉じ、状態を `stalled` に
  する。「何も起きていない」と「何も測っていない」が同じ見た目になるのを防ぐ。
  既定は 1500ms（48kHzでチャンク17回ぶん）。短くするとタブ切り替えやGCの
  一瞬の詰まりで止めてしまい、長くすると止まったことに気づくのが遅れる。
- `wakeLock` — 画面の自動ロックを best-effort で抑止する。長時間運用のためではなく、
  数分の計測を端末の30秒オートロックが黙って殺すのを防ぐだけ。
  取れなくても失敗にしない。

**開いたまま「止まっています」と出すのではなく、マイクを閉じる。** 再開したときに
必ず作り直した解析器で測り直すためである。途切れた前後のフレームが同じ移動窓に
混ざると、10秒平均が実時間の何分にもまたがった値になる。閉じるので録音インジケータも
消える。

`onStop(reason)` に理由を渡すのは、**中断は停止と同じではない**からである。
理由は `user`（利用者が止めた）/ `stalled`（計測が途切れた）/ `failed`（起動に
失敗した）の3つ。利用者が止めたなら全部捨ててよいが、中断と起動失敗には
「再開したら続きから読みたいもの」がある——ボリュームなら基準値、ハウリングなら
止まる直前に捕まえた周波数。`failed` を分けていないと、**「基準は保持しています」と
出した直後に再開が失敗し、その基準を黙って捨てる**という最も質の悪い裏切り方をする。
再開時は `onStart` に `previousDeviceLabel` を渡すので、機能側は
**同じ機材が戻ってきたか**を確かめられる。

## UI の共通形

```
[ 主役の値（大きく） ]      ← ハウリングなら状態と周波数、ボリュームなら基準との差
[ 補足の一行 ]             ← 帯域名、あるいは何の平均かの断り
[ 帯域バー or レベルバー ]  ← 100ms ごとに更新
[ 停止ボタン ]
```

停止したら `idle` に戻るだけで、結果画面には遷移しない。

**主役の位置は空けない。** 値がまだ出せない間（窓が埋まるまで、基準を取るまで）は
待ち状態を言葉にしてそこに置く。大きい表示が消えると「終わってしまった」と読まれる。

## 更新レートとレイテンシ

見ながら操作する道具なので、レイテンシが製品価値そのものになる。

- hop は 100ms。表示の更新間隔もこれに合わせる
- FFT長は機能ごとに違う。ボリュームはFFTを使わず（A特性のIIR）、ハウリングは
  4096（48kHz で 11.7Hz 分解能・85ms）。音質チェックの 2048 は流用しなかった——
  低域で突出判定に使えるビンが足りない
- ハウリングの持続判定は 250ms（3フレーム）。設計時の 500ms から詰めた。
  腕のいいオペレーターはハウリングを 0.2〜0.5秒で殺すため

48kHz では窓(85ms) < ホップ(100ms) なので、フレーム間に約15msの見ていない隙間がある。
持続する現象を見る道具なので実害は無いが、隙間があること自体は把握しておくこと。

「表示用の短期履歴」と「終了時サマリ用の長期履歴」は別物である。前者は判定に必要なので
持つ。後者は作らない。
