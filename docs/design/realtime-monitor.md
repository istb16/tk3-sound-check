# 設計: 受動リアルタイムモニターの骨格

対象: ハウリングチェック / ボリュームチェック
状態: **マイクの取り込み層のみ実装済み**（`src/lib/audio.ts` の `startMonitor`）。
[ボリュームチェック](./volume.md)が唯一の利用者。

## どこまで共通化してあるか

抽象は利用者が現れてから切り出す、という順番で進めている。利用者が一人もいない層は
正しさを検証できず、次の機能を書き始めた瞬間に「合っていない」と分かるためである。

したがって現時点で `src/lib/` にあるのは**マイクの取り込みだけ**（`startMonitor`）。
これはボリュームチェックが実際に使っており、動作が確かめられている。

解析・状態機械・画面はボリュームチェックの中にある。**ハウリングチェックを書くときに、
利用者が2つ揃った状態で共通部分を切り出す。**

## 音質チェックと同じ形にしてはいけない理由

| | 音質チェック | ハウリング / ボリューム |
|---|---|---|
| 取り込み | 10秒で自動的に終わる | 終わりが無い。止めるまで聞き続ける |
| 状態 | `idle → recording → analyzing → done` | `idle → listening`（`done` が無い） |
| 出力 | 100点満点の採点と静的な結果画面 | 刻々変わる状態表示。点数という概念が無い |
| 終了時 | 結果が残る（保存・再生できる） | 何も残さない（履歴もサマリも作らない） |

同じ状態機械に乗せると両方が歪む。`AppState` を共有しないこと。

## 共通化するもの / しないもの

**する**

1. マイクの獲得と `AudioContext` のライフサイクル（`src/lib/audio.ts`）
2. 信号処理プリミティブ（`src/lib/signal.ts`）
3. シェル（ヘッダー・ルーティング・言語・`src/shell/app.css` のパネル）

**しない**

- 解析パイプライン（`analyzeSamples` の「バッファをもらってスコアを返す」形）
- 状態機械
- `VuMeter` / `RadarChart` / `ScoreBreakdown` / `VerdictPanel`（すべて音質チェック専用）

## 実装済み: `audio.ts` のストリーミング取得

既存のワークレット（生PCMを main thread へ流す仕掛け）はそのまま使えた。
`setupRawCapture()` が `parts[]` に溜めていた部分を外し、都度コールバックへ渡すだけで
ストリーミングになる。配線は `attachPcmWorklet()` に切り出して両者で共有している。

```ts
export interface Monitor {
  /** マイクを閉じ、AudioContext を破棄する。二度呼んでも安全 */
  stop: () => void;
  /** 解析側が周波数を扱うために必要 */
  sampleRate: number;
  /** 実際に開いたマイクの名前 */
  deviceLabel: string;
}

export function startMonitor(
  onChunk: (samples: Float32Array) => void,
): Promise<Monitor>;
```

`recordMicrophone()` はこの上に実装し直せる（一定時間ぶん溜めて止める）が、**移行は
必須ではない**。音質チェックは動いており、動いているものを触る理由が無い。

実装して分かったこと：

- `AudioContext` は自動再生ポリシーで `suspended` から始まることがある。
  動かないと `process()` が呼ばれないので、`resume()` してから配線する。
- `stream.getAudioTracks()[0].label` で開いたデバイス名が取れる。
  `enumerateDevices()` を呼ぶ必要はない。
- A特性のようなサンプルレート依存の係数を持つ解析は、`AudioContext` のレートが
  確定してからでないと初期化できない。**最初の数msぶんのチャンクは捨てる**設計にした。

## 取り込み時の制約（全機能で共通・変更禁止）

```ts
{ echoCancellation: false, noiseSuppression: false, autoGainControl: false }
```

音質チェックではノイズフロアと音量を測るために必要だった。ハウリングでは
**より強い理由がある**——エコーキャンセラは、まさに検出したい発振をブラウザが
先に消してしまう。この3つがONの状態でハウリングチェックは成立しない。

## まだ共通化していないもの

ボリュームチェックが持っているが、利用者が1つしかないので `lib/` へ出していないもの：

- **フレーム化**（チャンクをまたいで100msごとに区切る）。ハウリングも同じ形が要る。
- **移動窓の集計**（直近N秒の平均・最大・回数）。ハウリングの「持続判定」も同じ形。
- **状態機械**（idle / listening / error）。

ハウリングを書くときに、両方の実装を見比べてから切り出す。

## UI の共通形

```
[ 主役の値（大きく） ]      ← ハウリングなら状態と周波数、ボリュームなら基準との差
[ 補足の実測値 ]           ← 帯域名、あるいは基準値と現在値
[ 帯域バー or レベルバー ]  ← 100ms ごとに更新
[ 停止ボタン ]
```

停止したら `idle` に戻るだけで、結果画面には遷移しない。

## 更新レートとレイテンシ

見ながら操作する道具なので、レイテンシが製品価値そのものになる。

- FFT は既存の `FFT_SIZE = 2048`（44.1kHz で 21.5Hz 分解能・46ms）
- hop は 100ms。表示の更新間隔もこれに合わせる
- 判定は 500ms の移動窓（数フレームぶん）で行う

「表示用の短期履歴」と「終了時サマリ用の長期履歴」は別物である。前者は判定に必要なので
持つ。後者は作らない。
