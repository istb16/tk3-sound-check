# 設計: ボリュームチェック

ルート: `/volume`　状態: **未実装（メニューに「準備中」で並んでいる）**
前提: [受動リアルタイムモニターの骨格](./realtime-monitor.md)

## この機能が答える問い

**「いま喋っている声は、録るのにちょうどいい大きさか。」**

喋りながらメーターを見て、その場でゲインを合わせるための道具である。

## 音質チェックの「音量」軸との違い

音質チェックは既に音量を測っている（15点満点、`factLevel` で dBFS を表示、
低すぎ／高すぎの助言も出す）。にもかかわらず別の機能として立てる理由は、
**タイミングが違う**からである。

| | 音質チェック の音量軸 | ボリュームチェック |
|---|---|---|
| いつ | 録った**後**。採点の一部 | 録る**前**。合わせるための鏡 |
| 何を返す | 15点満点の点数と助言 | いまこの瞬間のレベル |
| 使い方 | 結果を読む | 見ながらつまみを回す |

同じ物理量（dBFS）を、別の目的で見せている。

## 原理的な限界（設計に織り込む）

**絶対音圧（dBA）は出せない。** ブラウザはマイクの感度を知らないので、dBFS からの
換算は原理的に不可能である。したがってこの機能が言えるのは
「フルスケールに対してどれくらいか」だけであり、
「部屋に対して大きすぎる／小さすぎる」は**言えない**。

画面にもそう書く。dBA を期待して開いた人が、それが出ないことを画面で理解できるように。

## 測るもの

100ms ごとに、その区間について:

- **RMS → dBFS**（`signal.ts` の `rms` と `dbfs` をそのまま使う）
- **ピーク絶対値** — クリップの検出用。`1.0` に達したサンプルの有無

新規の信号処理は無い。既にあるものの組み合わせで足りる。

## 3段の判定

閾値は音質チェックと同じ値を使う（`AudioAnalyzer.ts` の音量軸）:

| 表示 | 条件 | 根拠 |
|---|---|---|
| 小さすぎる | 発話レベル < -30 dBFS | `ADVISE_LOW_DBFS`。ITU-T P.56 系が有効音声レベルを -26dBov に正規化することと、民生機材の実測（-26〜-47dBFS）から |
| ちょうどいい | -30 〜 -12 dBFS | `IDEAL_HI = -12` |
| 割れている | ピークが 1.0 に到達 | クリッピング |

**閾値の定数は音質チェック側から import せず、この機能が自分で持つ。**
採点の尺度（満点＝スタジオ品質）と、合わせるための基準は別物であり、
片方を動かしたときにもう片方が黙って壊れるのを避ける——README にある設計方針と同じ。

ただし**値が食い違ってはいけない**。同じ音を音質チェックとボリュームチェックに
通して、判定が矛盾しないことをテストで固定する。

## 無音の扱い

喋っていない区間のレベルを「小さすぎる」と表示すると、メーターが常に赤くなって
役に立たない。**発話区間だけを見る。** `estimators.ts` の `separateActiveFrames` と
同じ考え方（フレームRMSの分布から有音・無音を分ける）を、100ms窓に対して適用する。

無音が続いているときは判定を出さず、直近の発話区間の判定を保持する。

## 状態機械

```
idle ──(開始)──> listening ──(停止)──> idle
  └──(マイク拒否・失敗)──> error ──(やり直す)──> idle
```

`done` は無い。止めても何も残らない。

## 画面

```
[ 小さすぎる / ちょうどいい / 割れている（大きく） ]
[ -18.3 dBFS ]
[ 横棒のレベルメーター。適正域を帯で示す ]
[ 停止 ]
```

ピークホールドは付ける（一瞬の割れを見逃さないため）。
音質チェックの `VuMeter` は総合スコアを表示するための部品なので**流用しない**。

## 実装の位置づけ

この機能は実質「マイクを開いて `rms` を 100ms ごとに出す」だけで、
[骨格](./realtime-monitor.md)そのものとほぼ同じ大きさになる。
ハウリング検出に比べて実装量は一桁小さい。

したがって**骨格が正しいことを最も安く検証できるのはこの機能**である。
ハウリングを実装する前にこちらを通しておくと、骨格の間違いが安く見つかる。
