# 設計: シェル（トップページとヘッダー）

対象: `src/App.svelte` / `src/pages/Menu.svelte` / `src/shell/`
状態: **実装済み**

## トップページは何か

**ランチャーである。** 開くのは3つの道具をすべて知っているが、使うのは月に数回という人。
だから位置では覚えていない。

したがって最適化するのは「何をする道具か説明すること」ではなく、
**読まずに撃ち分けられること**である。以前のメニューは3枚とも同じ形・同じ色の
カードで、違うのは中の文字だけだった——毎回**読んで**選ばされていた。

ただし `index.html` に Google Analytics が入っており、**これは公開サイト**である。
README は GitHub にしかなく `/` が唯一の着地面なので、初めての人も実際に来ている。

## アイコン

**その道具の画面の縮小図**を描く。一般的な比喩ではない。

| 機能 | 図 | 色 |
|---|---|---|
| 音質チェック | 5軸のレーダーチャート | 青緑 `#006E80` |
| ボリュームチェック | 基準マーカー付きの水平レベルバー | 藍 `#2E4B8F` |
| ハウリングチェック | 1本だけ突出したスペクトル | 琥珀 `#A85400` |

シルエットが五角形／横棒／棘のある山と最大限に違うことが唯一の要件である。
意味が読めることは要件ではない（開く人は3つとも知っている）。

**マイクは描けない**——3つとも全部マイクを使う道具なので、同じ絵が3枚並ぶだけで
見分けの役に立たない。スピーカーも波形も同じ理由で弱い。

**ハウリングに⚠は使わない。** 予兆を出さない・危険と断定しないと決めた道具が
「危険を知らせるアプリ」に見える。

アイコンの実装は手書きのインラインSVG。実行時依存が Svelte だけなので、
アイコンライブラリ・絵文字・画像はいずれも方針と合わない。

## 色

**赤（`#B00020`）は「何かがおかしい」専用**に予約してある——音割れ・発振中・
マイク拒否・計測停止の4つが赤である。だから機能色に赤系は使わない。
`App.test.ts` が色相差で機械的に守っている（警告の赤から35°以上離れていること、
互いに25°以上離れていること、白地で 4.5:1 以上のコントラストがあること）。

琥珀を `#B86000` ではなく `#A85400` にしているのは、前者だと白地でのコントラストが
4.46 で、戻るボタンの文字色として 4.5:1 をわずかに割るためである。

**機能色はメニューのタイルと、機能ページの戻るボタン・タイトル下線まで。**
ページの中身（バー・ボタン・フォーカスリング）には持ち込まない——ハウリングの
突出度バーもボリュームのレベルバーも、閾値を超えると `--accent` から**赤に変わる**
ことで異常を示している。基調色を赤に近づけるほどその変化が読めなくなる。

色が乗るのはアイコンのチップ（角丸の色ベタ）だけで、カードは白地のまま。
この道具は照明の暗い会場や逆光の窓際で開かれるので、本文の背景を白から外さない。

## ヘッダー

**主役はページによって入れ替わる。**

```
トップページ                        機能ページ

                     [JA|EN]      ┌ ← メニュー ┐        [JA|EN]

    SOUND CHECK                          音質チェック
耳では分からないことを、                    ────
その場で数値にする。
```

「大きいロゴは押せない」が web の常識なので、**看板を目立たせるほど「押せば戻れる」
は伝わらなくなる**。以前は製品名の1要素に看板と戻る手段の2役を負わせていたが、
役割を分けた。トップには戻り先が無いので看板は押せなくてよく、機能ページでは
その人はもう中にいるので看板は要らない。

戻るの文言は行き先の名前（`メニュー`）にしている。`SOUND CHECK` は行き先が何なのか
言っていないが「メニュー」は言っており、スマホの左上は最も届きにくい場所なので
短いほうがよい。**画面下には置かない**——測定中の `停止` と的が並ぶと、押し間違えて
ボリュームの基準やハウリングの捕まえた周波数を失う。下だけに置くとスクロールするまで
出口が見えず、直そうとした不満そのものが再発する。

機能ページから看板が消えるぶんは、タブのタイトル（`音質チェック | サウンドチェック`）
が受け持つ。

看板の綴りは英字固定（`WORDMARK`）である。JA/EN を切り替えるサイトでは、
**翻訳しなくて済む名前のほうが看板に向く**。

## 一行の説明

> 耳では分からないことを、その場で数値にする。
> 会議の録音環境から、会場のPAまで。

主な仕事は説得ではなく**安心**である。名前と3つのボタンしか無い画面は、説明を
省いたのではなく書き忘れたように見える。

誇張しないこと。この製品群は「dBAは原理的に出せません」「点数は判定ではありません」
と言い続けてきた。看板だけ誇張していると信用が落ちる。**手軽さは謳わない**——
ブラウザで動く音声ツールは他にもあり、このサイトが違うのは測っている中身の厳密さで、
手軽さを謳うと一番強い部分を自分で隠すことになる。

## レイアウトの制約

**375×667（iPhone SE）で3枚とも一画面に収まること。**
スクロールしないと選べないランチャーは、いまより遅い。
`App.test.ts` が3枚目の下端を実測して守っている。

タイルは横長の行で、スマホ1列・PC 3列（`repeat(auto-fit, minmax(280px, 1fr))`）。
**3つは2列に収まらず必ず1枚余る**ので、2列になっていないことをテストで見ている。

`main` の幅はページの種類で変える。機能ページは読む幅、メニューだけ全幅
（3枚を1行に並べるため）。中央寄せは flex ではなく `margin-inline: auto` で行う——
body を flex にすると間に挟まる `#app` が中身に合わせて縮み、その中の
`inline-size: 100%` が効かなくなる。

タイルは `<button>` ではなく本物の `<a href>`。公開サイトなので、これだけで
「長押しでリンクをコピー」「新しいタブで開く」が効く。修飾キー付きのクリックは
ブラウザに渡している。

## 幅で判断する、ビューポートで判断しない

`main` の幅はビューポートの 55vw なので、**ビューポート幅で列数を決めると外れる**。
音質チェックの結果は以前 `@media (min-width: 768px)` で2列に割っていたが、
1280px のビューポートでも `main` は 704px しか無く、しかも当時は半分幅の項目の次が
必ず全幅の項目だったため、**右カラムがずっと空**だった。

いまは結果領域にコンテナクエリを張り、**その領域の幅**が 640px を超えたときだけ
2列にしている。対になる相手も付けた（総合点↔判定、レーダー↔内訳）。
1列のときの読む順（総合点 → 判定 → レーダー → 内訳）は変えていない——
判定がこの機能の答えなので、レーダーより先に出す。
